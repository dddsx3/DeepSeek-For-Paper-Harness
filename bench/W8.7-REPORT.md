## 1. P1 —— reasoning 通道结清（决定性数据）

三支探针（raw SSE 全落盘）：

| 探针 | 任务类型 | reasoning 字符 | content 字符 | 比值 |
|---|---|---|---|---|
| mini | 输出 `{"ok":true}` | 0 | 11 | — |
| mid | 算术+解释 | 265 | 79 | 3.4:1 |
| **ir（同构）** | **ir-container 声明** | **6,863** | **469** | **14.6:1** |

**三假设判定**：(a) reasoning 通道吃预算 **✅ 成立**；(b) 未解析字段 **❌ 排除**；(c) 中转吞 content **❌ 排除**（content 完好到达）。

**W8.5 完整机理**：模型先花 ≈15 倍内容的推理 tokens，32k 上限中留给 JSON 的只有 ~2k → 大容器写不完 → 截断。**这决定 P2 片长**：每片内容 ≤ 600 字符 ≈ 9k 预算占用。

## 2. P3 —— 路由按方法构成重标（O-L1-04 修复）

**旧问题**：词频投票会把 2024-C 判为 F4（有契约）放行——真实的 F2 缺口被"碰巧存在的契约"掩盖。

**新规则**（`route.ts` 重写）：识别**全部方法组件**（词表对齐核验表 Part B，优化→F2 而非 F1）→ **任一组件无契约即拒绝**（点名缺哪个）。

**实测验证**：
- 2024-B：组件 F4×4 + F3×3 → 全部有契约 → **放行**（与真值 F3+F4 对齐）
- 2024-C：组件 F3×4 + F4×4 + **F2×2** → **拒绝（"其中 F2 尚无已实现的契约…混合题必须先补齐缺失组件的契约"）**——W8.5 的浪费因果链在源头切断

## 3. P4 —— per-run output-token 预算门（O-L5-03）

- **为什么必须是 token 门**：USD 日预算在 pricing 未配置时恒不触发（W8.5 的 75,669 output tokens 全在无上限下烧掉）。
- 实现：`maxOutputTokensPerRun`（executor options / `PAPER_MAX_OUTPUT_TOKENS_PER_RUN` env），累计 output 超限 → run **paused** + `budget_exceeded` 审计（kind=output_tokens_per_run）；**budget-exhausted 直接冒泡不重试**（重试=继续往刚撞破的天花板烧）。
- 验收 3/3：超限暂停 / 未超限正常 / 0=无界（历史行为保留）。

## 4. P2 —— 分片声明协议（O-L1-03，W9 主体前置）

- **设计**：一次性大容器 → 三片小输出（definitions / models / runtime），各片独立请求独立预算（片长按 P1 的 14.6:1 比值定），合并为一个容器后走**完全相同**的 producer/生产链/审计（合并点是唯一新代码）。
- **默认关闭**（`--shard-declare` opt-in）：W8.6 教训——未验证的协议改动不得直接改默认路径。
- 验收 8/8：三片合并入库 / 截断片按 TRUNCATED 归类 / 坏片保持 W4 归类 / 默认关（单次路径不变）/ SHARD_NAMES 闭集 / 围栏容忍 / 合并形状与单次一致 / 提示词规范。
- **本轮发现（已入台账 O-L1-10）**：**写路径不可重入** —— producer 成功写 store 后若后续（生产链）失败，重试再次合并/声明会 `duplicate_id`。分片路径暴露了它，但**单次路径同样潜在**（该缺陷独立于分片）。
