### 2.3 B 组 —— E2 字段层合规（本轮单变量）

**B1 DRIFT 引导回灌**（`produce/e2-guidance.ts`，新文件 190 行）：
- ① 引用类型约束 —— **派生自 `IR_REF_FIELDS`**（单一真相源，不手写，避免与校验器漂移）
- ② 已注册 id 清单 —— 从 canonical store 快照取

**关键实测发现（B3 回放副产物）**：② 是**预防性**的，首次尝试即携带（run-4 首试 guidance = 985 字符，只含 id 清单无 violation）；③ 才是**纠正性**的，只在被拒后出现。原断言"首次尝试无 guidance"**过窄**，已改为"首次尝试无**纠正**"。

**B2 回灌文本零数字**：`stripNumericLiterals` 用 `#` 替换而非断言——理由写在模块头：raw reason **可能**含数字（字节偏移、行号），断言要么拒绝有用信息、要么逼调用方手写文案，**而手写正是 A1 丢失分类的成因**。id 清单逐字保留（`P1` 带数字，剥离会指向不存在的 id）。

**B3 cassette 指纹**：见 §1 H9（无 miss，根因是结构性的）。

**B4 `reasoning_effort` 角色区分探针**（**只探不改**，红线 N14）：

### 2.4 C 组 —— Q 支线（并行，独立归档）

**C1 DP-4 spike**：**部分能**——边界恰好落在「数值 vs 结构」上。
- **能捕获**：`dt` / `N` / `solver_config.rtol` 这类**标量数值**，经 `code → jsonPath → Result` 逐个读回；实测驱动真实 node 子进程，4 个配置数字全部铸成 Result，且从字节**独立重算**与 store 值一致。
- **不能捕获**：`solver_config.method: "RK4"` 这类**非数值**成员、以及整个 `solver_config` 对象（`Result.value` 是 `zod.number()`，`ir/schema.ts:236`）。
- **两个对 M5 有实质影响的发现**：① `ModelSpec.parameter_refs[].value` 是模型可写的数字字段，但**不是捕获通道**（不来自任何 run，无 `code_hash` 钉住）；② **`seed` 是现成的反面教材**——它被捕获进 `ExecutionRecord`，但 runner **从不把它交给子进程**（`runner.ts:97-109` 无消费者）。这证明**「配置进了 IR」≠「配置影响了这次执行」**；若 M5 的 `dt` 走同一条路，"配置复现"会变成空断言。**M5 必须走「由 code emit」形态。**

**C2 接缝验证**：**真正会撞的不是 `.strict()`，而是 `refs.ts` 的 null 不容忍。**
- 14 个规格字段中 **12 个**加进现有 kind 会被 `.strict()` 拒 → `CapabilitySpec` **必须是新 kind**（规格这点判断正确）。
- **但更危险的是**：`required_output_ref: null` / `at_config_ref: null` 会被 `refs.ts` 拒绝（`validateRefFields` 的 single/nested 分支**无 null 短路**，`Map.get(null)` → `unresolved_reference`）——**schema 放行、下游拒绝、失败原因还伪装成"引用不存在"**。全仓**无任何** `refSchema.nullable()` 的 IR 字段，此通路从未被走过。
- **W8.12 落地前必须先改 `ir/refs.ts` 的 null 容忍与复合路径解析**，否则会撞的不是 `.strict()` 而是**更难诊断的 `unresolved_reference`**。
