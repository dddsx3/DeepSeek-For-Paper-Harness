## §2 各条实现与证据

### 2.1 A1 —— 锚点 id 必须是"可被引用的名字"（解 B3 反向）

**事故（run-4/W8.10）**：E1 写 `[[ASSUMPTION: ...]]`，反向检查报"E1 标记了但 IR 未声明的假设：..."——读者无法分辨是漏声明还是占位符。根因：指令只说"别写 `<your-short-id>`"，**从没说过"这个 id 会被下游逐字引用，所以它必须是一个名字"**。

**修法**：指令补上**理由 + 正反例**；新增 **B5 规则**（`isUsableAnchorId` = `isIrId(id)` 且含至少一个字母/数字）。

**关键的方向性决定**：实测 `idSchema` **比任务书设想的宽松得多**——**中文 id 是合法的 IR id**（`problem-contract.ts` 明言 IR 刻意不折叠兼容等价字符）。故**不引入字符集收紧**，否则会对 IR 本来接受的 id 制造假红（红线 N2）。有专门测试钉住。

### 2.2 A1b —— 行内标记是散文，不是声明（修 B5 假阳性）

**A1 落地后的第一次真实运行（run-1）立刻抓到 B5 的假阳性**：E1 在正文里**引用**了这个语法——"这三处都在上文以 `[[ASSUMPTION: ...]]` 标注。"——解析器用 `indexOf` 扫全文，把散文里的引用当成声明。

**E1 其实写对了**：它的 **16 条真锚点全部行首**，契约（"on its own line"）100% 被遵守。**解析器比契约更宽，宽出来的正是假阳性。**

**修法**：`isLineStartMarker` —— 标记之前**只有结构标记**（空白/Markdown 列表符号）才算声明。真实数据验证：修复前 17 处 → 1 处假阳性；修复后 **16 条真锚点一条不少，假阳性为 0**。

### 2.3 A1c —— 讲义补上 `parameter_refs` 的元素形状

**run-2**：fidelity 门**第三次尝试全过**（21/21 逐字锚定）后，被封闭 schema 拒绝：`parameter_refs.0: expected object, received string`。

**根因**：`parameter_refs` 是讲义里**唯一**没给元素形状的字段——它作为裸名字列在 `variable_refs` 旁边，而后者**确实**是纯 id 列表。模型合理推断三者同形。字段需要对象是因为**参数携带绑定值**（零数字通道的要点）。

**测试带防漂移断言**：用 schema 真解析讲义里的正例（成功）与模型实际写的形状（失败）——**否则是在教一个 harness 会拒的东西**。

### 2.4 A1d —— 引用目标写进 E2 清单

**run-3**：`minted_ir_count` 首次达 **32**，fidelity 门**第三次尝试全过**（14/14）后，被 store 拒绝：`'S-P1' resolves to SymbolSpec, expected Result,DataArtifact`。

**根因（第三处信息不足）**：讲义只列**字段名**，从没说每个引用字段指向哪些 kind。且 `declarableRefRules()`（回灌用的表）**漏掉了 AssumptionSpec/EquationSpec/SymbolSpec——正是模型声明最多的三个 kind**，所以回灌也救不了。

**修法**：补齐三个 kind；E2 checklist 新增第 6 条**逐字段列出合法目标**，由 `declarableRefRules()` 派生（与校验器走同一张 `IR_REF_FIELDS`），**不可能与 store 的执行规则漂移**。首次尝试即带上，不靠回灌。

### 2.5 B2 —— E1 全文与 E2 容器落盘（红线 N17）

`spec.ts` 注释自述 "content is stored separately by a later provider"，而那个 provider **从未被实现**——`storeArtifact` 只写元数据 `storageKey: 'inline:<digest>'`，正文哪里都没有。于是"疑似改写"判定**事后无法核验**。

**修法**：新增独立存储域 `paper_artifact_body`（不挂 `paper_workflow`：那是 version 1，加表要么改 version 让已有数据读不出来，要么 schema 与磁盘不一致）。写入点：`storeArtifact`（唯一 choke point）+ 接收层 E1/E2（每 attempt 一份，可 diff）。正文过 `redactSensitiveText`；`getVerified` 校验正文与元数据 digest 一致。

**红线 N17**：只进 artifact body 域，不进节点输出（W8.9-C2 的 cassette 全 miss 教训）——有专门测试断言 body id 不出现在任何 prompt 与节点 public 输出。

**真实运行见证**：run-1 落盘 120KB（E1 全文 19665 字符 + 2 份容器）。**正是它让 §2.2 的假阳性和 §B3 的裁决成为可能。**

### 2.6 C1 —— 诊断文案从结构化字段生成（O-L5-07）

**事故**：文案表按失败码设计，真实失败是多条件组合，逐个修分支已复发三次。最严重的是 `none` 分支说"模型没有给出可用结构"，而 run-4(W8.10) 的 E1 有 14010 字符、两条 PASS——**与事实相反**。

**修法**：`failureFactsOf`（从 audit 投影 gate/失败规则/通过规则/E1 字符数）→ `fidelityBlockedHuman`（生成文案）→ `ruleSide`（归属，**复用** `executor.ts` 的 `E1_SIDE_RULES`，不是新语义）。

**真实 run-4 数据上的对比**（旧 → 新）：
```
旧：调用/传输失败（gate-failed）… → 重试一次；若持续失败报告给维护者。
新：模型已产出 14010 字符的建模分析，但**接收层的保真检查未通过**…
    未通过的检查：B3 反向、B3 正向。已通过：B4、B3 锚点同一性。
    → 这类失败发生在**规范化侧**…失败 gate：ir_producer（DRIFT guidance budget exhausted）。
```
**run-4(W8.11) 实际打印了正确文案**（截断类）："撞到提供方的输出长度上限被截断（**不是题目或模型违规**）"。

### 2.7 D1 —— `refs.ts` 的 null 容忍 + 复合路径（W8.12 前置）

- **null 短路**：显式 `null` = "该引用不适用"，合法（`undefined` 不等价，保持原行为）。此前 `resolve(null)` → `Map.get(null)` → 报"引用不存在"——**schema 放行、下游拒绝、失败原因伪装**。
- **复合路径** `splitCompositeRef`：`<Kind>:<id>.<field>`（规格用的形式，全仓此前无解析器）。**只解析，不改含义**：非 kind 前缀（`run_output:...`）不被当复合引用，既有引用零行为变化（1261/1261 全绿为证）。

### 2.8 D2 —— 6 个闭集常量落到 `paper-foundation`

`capability-sets.ts`：`FAMILIES`/`MACHINE_CHECK_KINDS`/`CAPABILITY_JUDGES`/`VERIFICATION_DEPTHS`/`THRESHOLD_OPERATORS`/`PROBE_IDS`/`BOUNDARY_IDS`，**每个的取值出处逐条注明**。`route.ts` 改为反向导入（`paper-foundation` 不依赖 apps，W8.12 一引用就会撞）。C2 曾记录 `PROBE-TYPOLOGY.md`/`HONESTY-BOUNDARY-CLASSES.md` "尚未入库"——**实测 12 份 docs/quality/*.md 均已被跟踪**，该警告已过时。
