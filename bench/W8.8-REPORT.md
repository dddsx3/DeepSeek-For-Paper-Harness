## 3. 阻塞原因（按贡献度排序）

1. **模型的协议遵从不足（主因）**：raw 证据显示模型**读懂了题**（run#4 首调自己指出"F4 不适合作为主模型：问题1采用 F3，问题2—3采用 F2"——与人工真值方向一致！），但在 12 条协议教学 + 契约 banner 之下，**选择输出分析文本而非 JSON 容器**。分片后（run#5/6）遵从度提升（每片都产出了合法小 JSON），但**跨片引用一致性**（分片 2 的 variable_refs 应引用分片 1 的 symbol_id）仍未对齐。
2. **上游空流（次因）**：run#3/4 的第 2/3 次调用遭遇 HTTP 200 + 空 SSE（无任何 data 行）——stealth 免费模型的限流/不稳定行为。已具备错误分类（in-band error 捕获），但空流目前仍落在 FINISH_REASON_UNKNOWN（应独立成类，见 §5）。
3. **stealth 模型的不稳定性**：429 限流反复出现（`temporarily rate-limited upstream`）；非流式 524。

## 4. 本轮的真实收获（缺陷修复 + 证据）

| 发现/修复 | 证据 |
|---|---|
| **构建陷阱**（最重要）：`tsc -b` 不更新 tsdown 的 lib——真实运行曾跑**旧 executor**（截断类/熔断/预算门/分片均不在链路上），而 vitest 直读 src 所以测试全绿。**教训已归档**："改 executor 后必须 `tsdown` 重建 lib 才能真实运行" | run#1–3 的失败链 vs run#4 的 raw SSE |
| **in-band error 捕获**（真实缺陷一）：OpenRouter 限流发 `{"error":...}` 后断流，旧解析器静默跳过 | `or-sse-raw.txt` vs V1 audit |
| **失败调用的 usage 入账**（真实缺陷二）：`ModelCallFailure` 携带 usage、runNode 在分类前 recordUsage | run#6：10 条 usage（4,564/3,760）vs run#1：1 条 |
| **O-L1-10 幂等重入修复**（W9-P2 期间发现，本轮实弹验证）：`produceContainerInto` Pass 2 对**已存在且内容相同**的条目幂等跳过；容器内重复仍拒；内容不同仍冲突 | run#5 duplicate_id ×2 vs run#6 无 duplicate_id；ir-producer.spec +2 测试（19/19） |
| **D1 容器摘录的实战价值**：run#5/6 的每次拒绝都带 head 摘录+hash+reason——**失败现在完全可诊断**（模型具体哪个字段填错一目了然） | `container_refused` 审计条目 |
| **分片协议的真实效果**：每片 200–700 tokens（远离 32k 上限）；失败模式从"截断/空流"（不可修）变为"跨片引用一致性"（可修——加片间上下文即可） | run#5/6 的 ShardOutput/ShardMerge 事件 |
| **路由重标的正确性被模型自己确认**：run#4 首调输出"F4 不适合作为主模型……问题1采用 F3，问题2—3采用 F2" | `raw-sse-run4-execute.txt` |

## 5. 下一步（按优先级）

1. **分片 2 的跨片上下文**（低成本、高预期收益）：把分片 1 产出的 symbol_id 列表显式喂给分片 2 的 prompt（"variable_refs 必须从这些 id 中选：[S-IN, S-OUT, ...]"）。run#6 的失败全部是这一处，改一处即可。
2. **空流独立成类**：HTTP 200 + 无 data 行 → `EMPTY_STREAM`（可重试但应计数；当前落在 UNKNOWN）。
3. **上游稳定性**：stealth 免费模型限流明显（429/524/空流）。建议用户确认限额，或备用一个付费路由做对照。
