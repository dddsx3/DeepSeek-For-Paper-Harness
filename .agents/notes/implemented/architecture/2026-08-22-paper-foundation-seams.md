# Agent Note: Paper foundation reuses storage and LLM seams

Status: implemented

English | [中文](2026-08-22-paper-foundation-seams.zh.md)

## Problem

The phase-two implementation needs durable workflow-run records, role settings, and a bounded provider diagnostic without introducing a second message protocol, persistence medium, or credential document inside the harness.

## Decision

The Paper rebuild ships on the upstream TypeScript/Cordis plugin architecture (`packages/*/*`, Zod schemas, storage-domain persistence, `ctx.llm` and `ctx.skills` seams). A FastAPI, Electron, or Python sidecar was considered and rejected: it would duplicate the upstream runtime and create a second source of durable state. This closes the product-form question for all later phases.

`@deepseek-ai/dsh-paper-foundation` is a host package under `packages/paper/paper-foundation`. Its versioned Zod records are declared once in `src/spec.ts` and opened through the existing `storage-domain` facility. `DomainWorkflowRunRepository` exposes typed run, node, event, artifact, and manifest operations while keeping backend details out of workflow consumers.

Role settings use the existing settings namespace mechanism and store only credential references. `PaperProviderService` resolves roles through `ctx.llm.resolveModelInfo()` and dispatches through `ctx.llm.stream()`, so DeepSeek remains an adapter-owned implementation. `PaperDiagnosticsService` performs a bounded cancellable request without creating a normal Session and returns only route, model, latency, and a stable status code. `WorkflowEngine` owns durable run/node state transitions and recovery reconciliation; `replayWorkflow` validates contiguous event history before recovery, and `WorkflowEngineService` runs that recovery during startup. `SignedSkillProvider` is an optional source on the existing `ctx.skills` registry; it validates manifest compatibility, declared file hashes, trust-root selection, and detached Ed25519 signatures before exposing a skill. `SkillCatalogService` owns durable install, version history, and rollback over its own `paper_skills` domain, rejects skill sets whose active tools or exclusive tag groups collide, and accepts unsigned packages only in development mode with `allowUnsigned`, never in production builds. `CatalogSkillProvider` serves the catalog's active versions through `ctx.skills`. The `paper.*` apiproxy domain exposes run control (`list/get/start/pause/resume/cancel`), resumable event reads (`events` with an `afterSeq` cursor over the durable log), and catalog operations, with structured `paper-*` error codes; both Paper services stay optional compositions. `WorkflowExecutor` drives plan, execute, the mode-bounded review loop (`resolveRunPolicy`: fast delivers after one revise round, strict allows three and fails when defects persist), and delivery with a manifest; every model call goes through the shared provider seam and every fact through the engine, so execution remains replayable. Durable events are pushed in-process as `paper/run-event` and forwarded to remote consumers through the `API_REMOTE_FORWARDED_EVENTS` allowlist (`host/remote-event` frames).

Retry, cost, and audit are separate seams the executor composes rather than logic inside the state machine. `classifyFailure` decides whether a provider failure retries, blocks, or needs a content edit; `backoffDelayMs` grows exponentially with jitter and never undercuts a provider-requested delay; a node that spends its attempts pauses for review rather than failing, so a resumed run continues from it. Cost is derived from token counts against a configured price table instead of trusted from a provider field, and `evaluateBudget` pauses a run once the day's ceiling is spent, with a raised ceiling for strict mode because it reviews more. `PaperAuditService` owns a separate `paper_audit` domain ordered by append sequence, because two operations can land in the same millisecond and a trail that cannot state which came first is not evidence; every detail map passes through `redactSensitiveDetail` first. Context budgeting is a fourth composed seam: `compactPrompt` prices labeled prompt sections under the repo's four-character density and trims them in declared priority order, so a regenerable plan gives way before the defect list, the draft, and finally the task, while instructions are never cut. A section that reaches its keep floor is retired so the next tier gives way instead of the pass budget spinning on one section, and a prompt that still cannot fit is sent as short as the module can make it — reporting an estimate above budget — rather than dropping a required section. Whatever is elided is stored as a run artifact and referenced from the request, which is how large content stays recoverable without being resent. Budget, backoff, retention, prices, and the context utilization fraction are validated service config, not constants.

Legacy migration and skill cleansing are the final composed seam, again split between pure translation and durable progress. `legacy.ts` normalizes the predecessor's settings and run vocabulary without opening its database: provider inference is a deployment-owned URL path-segment table, unknown enums fail rather than being guessed, and an inline API key becomes a `CredentialPlacement` for the existing credentials seam while the new settings record keeps only its reference. `LegacyMigrationRunner.plan()` and `apply()` invoke the same translation; the former writes nothing, while the latter writes records keyed by their new ids and records a per-legacy-id completion mark only after the run, nodes, and contiguous event log land. This is deliberately resumable rather than falsely transactional across many storage writes: a pass interrupted before the mark retries keyed writes and skips event sequences already present, a pass interrupted after the mark skips the bundle, and the legacy source is never deleted or edited. Every start, record, skip, refusal, and completion reaches `paper_audit`. `cleanseSkillBody` turns provider-specific XML-style blocks into neutral fenced blocks while keeping content, removes instructions that name a predecessor command-line tool or bypass the live permission surface, and drops directives that assume a parseable provider reasoning channel. Every rewrite reports a rule id, original line, and excerpt; a person reviews the output before it is signed. The composition mounts a migration runner but never starts a migration during boot.

Self-update is a fifth composed seam, split between a pure verifier and a durable recorder. `verifyReleaseManifest` judges one manifest — schema, harness floor, trust root, detached Ed25519 signature over the stable-JSON payload minus the signature block — and `verifyReleaseArtifacts` checks each artifact's size before its SHA-256, so a truncated download is refused before it is hashed. The update feed is a caller-supplied reader rather than a URL this package opens, which keeps the deployment in charge of whether updates are reachable and keeps tests off the network. `isInRollout` resolves a staged rollout as a pure function of install identity and version (SHA-256 bucketed into basis points), so an install that is in a rollout stays in it across restarts instead of re-drawing a lot every start, while a held-back install can still be offered the next version. `PaperReleaseService` owns the durable half over its own `paper_releases` domain: it mints one stable install id, refuses to stage anything unverified or not yet offered, records which version is active and which it replaced, and rolls an activated-but-never-confirmed-healthy version back to its predecessor during startup reconciliation — a bad release cannot strand an installation on itself. Staging, activation, and rollback reach the audit trail through the optional audit service. What the service deliberately does not do is move files or restart the process: it decides and records what should be active, and the installer that calls it performs the mechanics, because a verification failure and a failed file copy are different problems with different recoveries.

## Alternatives considered

- Adding a second Python service and database would duplicate the upstream runtime and create two sources of durable state.
- Defining a new Paper message or provider interface would duplicate `GenerateOptions`, `StreamChunk`, and `LlmFailure` already owned by `dsh-llm`.
- Storing credential values in the Paper settings record would violate the existing credentials seam and make ordinary settings reads unsafe.
- Having the release service copy artifacts and restart the process would put installer mechanics inside a service whose job is deciding what should be active; the two concerns fail differently and belong apart.
- Opening an unknown predecessor SQLite database inside the migration service would couple translation to one untrusted storage layout; the operator-supplied reader owns extraction, while this package validates and translates rows.
- Automatically cleansing a skill during catalog install would silently change model-visible behavior under a signature boundary; cleansing produces an unsigned review artifact first.

## Consequences

The package requires the existing storage-domain, settings, credentials, and LLM services in a composition. The workflow domain is stamped at version 1, and the skill, audit, release, and migration sidecars are separate version-0 domains; every one rejects incompatible media through the shared storage backend. Delivery is one profile layer: `@deepseek-ai/dsh-paper` under `packages/paper/paper-bundle`, whose `cordis.patch.yml` inserts the composition, the skill catalog, the catalog provider, and the invariant companion over `dsh-base` and a mode bundle. Because the rows pend on their injections, a profile that lacks storage mounts them and never activates them, so the bundle plugin names the missing services once at load instead of leaving that silence unexplained. The layer's shipped defaults are deliberately inert — no price table, no trust root, `allowUnsigned: false` — so a deployment must opt into spending and into updates.

## Testing

Both compiler faces build without errors, and the package meets the repository's per-file 100% coverage gate: schema, storage, provider, diagnostics, settings, workflow, replay, context budgeting, cost, resilience, redaction, audit, skill catalog, release verification, release state, legacy translation, migration progress, skill cleansing, and apiproxy paper-domain suites all run without network access. The bundle's own suite parses the shipped `cordis.patch.yml` through the loader's entry-list schema, so a row renamed in the patch fails the build rather than a profile at load. The release-state suite drives stage, activate, confirm, and rollback over the in-memory storage backend and reopens the same media to prove the install id survives a restart and that an unproven version rolls back on the next start. The package invariant companion checks undeclared domain tables and persisted values against the declared schemas.

`tests/workflow.e2e.ts` is the real-API acceptance suite and self-skips without `$DEEPSEEK_API_KEY`, so a keyless lane stays green. It asserts durable facts rather than model prose — manifest, artifact, accumulated usage, audit trail, and a replay of the event log agreeing with the records — and deliberately omits a strict-mode case, whose four reviews would spend four times the calls to pin facts the unit suites already cover.
