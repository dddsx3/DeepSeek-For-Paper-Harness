# Lean 形式化验证引入评估（2026-10-27，S1 咨询件）

> **问题**：当前使用环境（中转弱模型 + Windows 单机 + CUMCM 型任务）下，是否有必要引入
> Lean 形式化验证，用于进一步解耦"模型的思考"与"harness 的落实"？
> **结论先行：不必要，不建议进入主链。** 它不解决当前任何已登记的阻断项；对 DPH 真实的断言
> 形态覆盖极低；且与现行环境（模型能力/工具链/项目头号风险）三面相冲。以"触发条件 + 低成本
> 中间路径"形式留档，触发条件满足时按 TASK 制重开。**此件为 S1 咨询件，采纳与否由用户签收。**

## 1. 先厘清概念：Lean 不"解耦"，它是又一条"落实"通道

DPH 的"思考/落实解耦"已经由四层机制完成：模型面白名单生产者（模型只能声明 5 种 kind）→
IR 唯一写者 → 代码执行取证（capture/replay/字节级复算）→ 独立审计。模型的思想产物**从未
被直接信任**——这已经是比"引入 Lean"更彻底的解耦。

Lean 的真实定位是**第五条验证通道**，与现有四条并列：

| 通道 | 验证的断言形态 | 成本 | 现状 |
|---|---|---|---|
| 代码执行 | "这个数等于 x" | 低（本就要跑代码） | ✅ 承重 |
| 独立审计 | "这段代码真的算出了这个数" | 低 | ✅ |
| 语义指纹（L4） | "这段文本和证据说的是同一件事" | 中 | ✅ |
| 对抗评审（L5）+ review | "这个建模/推导在语义上站得住" | 中 | ✅/🟡 |
| **符号通道（sympy v7）** | "这个等式变形/方程解是对的" | 中 | 🟡 接链待核实 |
| **Lean（若引入）** | "这个定理/不等式/存在性命题为真" | **极高** | ❌ |

即：Lean 与 sympy 符号通道是**竞品**，不是对现有解耦的加强。

## 2. 需求侧：DPH 实际交付的断言形态，Lean 能盖住多少？

对 2024B 真实运行产出的断言做形态分析（PENDING-FIXES 四条致命缺陷是最直接的样本）：

- **F-001**（Δ、β 未登记）：信息完整性问题——门禁/教育问题，形式化无能为力；
- **F-002**（U_v 漏除交付概率 q_v）：**单位/口径错误**——property-based 测试（随机输入 +
  量纲不变量断言）一个下午能钉住的形态，Lean 形式化反而要先把整个 DP 模型形式化；
- **F-003**（根节点删掉调换损失项）：同上，守恒/边界不变量类；
- **F-004**（p̂=x/n 与 CP 区间依赖不存在的观测）：**题意理解错误**——语义层问题。

结论：**CUMCM 型任务的断言绝大多数是"计算结果"（执行通道已盖）+"统计程序口径"（审计+复算）
+"题意理解"（语义通道）**。Lean 能盖住的"定理型命题"（不等式、存在性、组合论证）在真实
缺陷史中占比为零——四次运行、25 次历史运行、9 次内测无一因"缺一个机器可查的定理证明"而失败。

## 3. 成本侧：三面相冲

1. **模型能力**：当前中转模型（v4-flash / glm-5.3-flash）不具备非平凡 Lean 能力——T3 填空
   （选择题级闭集）尚需统计资格门才 14/14 QUALIFIED，Lean 是自由证明级，能力差 3 个数量级。
   开源证明器模型（DeepSeek-Prover-V2 等）存在且开源，但它们是**专用模型**：引入即新增一条
   模型族通道（探针/注册表/串行预算全套成本），且 autoformalization（自然语言命题→Lean）本身
   仍是未解难题——把"写对证明"换成"形式化对了没"这个新假红源。
2. **工程面**：Lean 4 + mathlib 在 Windows 单机的工具链部署（GB 级依赖）、Pantograph/LeanDojo
   集成、证明失败的归因体系——每一项都是新的"假红"重灾区，**正好撞在项目头号风险（形态 6 /
   门禁假阳性，当前 STAGE-3 战役的核心痛点）的枪口上**。在最缺"判定可信度"的时刻引入最难
   校准的判定器，方向错误。
3. **原则面**：上限解放架构 P2"约束成本按需"（DORMANT→WARN→ENFORCE）——为一个零频断言
   形态常驻最高成本通道，违反自家宪法。

## 4. 生态现状（2026-10 调研）

可行性的证据确实在快速积累：[DeepSeek-Prover-V2](https://huggingface.co/deepseek-ai/DeepSeek-Prover-V2-7B)
（开源，recursive subgoal 管线，含 7B）、Goedel-Prover-V2（开源 SOTA）、Seed-Prover（形式化
约 78% IMO 历史题）、[Pantograph](https://github.com/leanprover/Pantograph)（机器对机器接口，
为 agent 而设计）、[LeanDojo-v2](https://leandojo.org)（训练/评测/部署全链）。
**判定**：三年内"按需启用一条 Lean 通道"在技术上完全可行——这不是"永远不做"，是"现在不做"。

## 5. 触发条件（满足任一即按 TASK 制重开本评估）

1. 真实运行中反复出现 review 在**数学命题等价性**上误杀/漏杀，且 sympy 通道（等式类）不够用；
2. 接入具备实证证明能力的模型，且能力探针显示该通道层内遵从率 ≥0.8（沿用 W5 升级纪律）；
3. 产品扩展到定理证明型交付（数论/不等式竞赛、论文的"理论证明"章节成为硬交付物）。

## 6. 中间路径（现在就可做，成本从低到高，覆盖 F-002/F-003 形态）

1. **property-based 测试**（hypothesis 类）：对模型代码按 DECLARATION 声明的不变量
   （守恒/单调/边界/单位）做随机输入断言——一次真实运行 F-002/F-003 的直接解药；
2. **量纲/单位检查**：DECLARATION 里声明每个量的单位，执行后自动核对（F-002 即单位错误）；
3. **强化 v7-sympy 接链**：等式变形/解方程类的机器核对（Lean 的低价替身，覆盖等式形态）;
4. **关键不等式的数值扫描**：对声明的不等式在参数域上加密采样验证（竞赛精度下"概率证明"
   足够，且完全复用现有执行通道）。

## 7. 一句话

**当前环境的正确问题是"让阶段 3 收敛、把门禁假阳性清零"，不是"加第五条验证通道"。**
Lean 是给"定理型断言"准备的答案，而 DPH 目前连"计算型断言"的全链验证还没跑通；
先把已建通道跑通，触发条件出现时 Lean 生态会比今天更成熟。
