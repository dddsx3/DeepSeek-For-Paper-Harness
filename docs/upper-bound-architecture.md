## 0. 一句话

**从"全程监护"改为"最小交规 + 事后严格验证 + 违规才介入"。**

harness 退出论文质量方程式的分子，只留在分母：它不再决定论文能写多好，
只决定**错误不会被静默放过**。

---

## 1. 设计原点：三个结构性封顶

这三条封顶不是猜测，每一条都有对应的实测现象。

| # | 封顶 | 现象 | 机制上的原因 |
|---|---|---|---|
| 1 | **伪自由** | 模型被要求"自由产出"，但 prompt 里 2 万字符的教学规定了它每一步该怎么做 | **知识**与**约束**都被编译进 prompt，且"门禁 ⇔ 教学一一对应"的同步测试把这种膨胀锁死成纪律 |
| 2 | **语义半盲** | 修复后复验只比对数值指纹，"换方法、增删方程、调整假设"这类语义修复**看起来毫无变化** | 复验判据只覆盖数值通道 |
| 3 | **解析排斥** | 解析推导只能以散文存在，进不了证据仓，得不到与数值结果同等的可信地位 | 零数字通道只管数值结论 |

三条封顶对应三种解法，合起来就是本架构的骨架。

---

## 2. 第一性原则

**P1 最好的产物不能被丢弃。**
自由分析是论文的**骨架资产**，结构化容器只是从分析中**抽取的验证视图**，
不反向驱动写作。

**P2 约束的成本应该按需提供，不是按户摊派。**
强模型不需要被教怎么写问题分析，弱模型需要。静态 prompt 区分不了两者，
"违规记录"可以。门禁默认静默运行只记录，首次违规注入一条**针对性的微教学**
（只讲被违反的那一条），重复违规才升级为硬拦截。

**P3 上限在选择点决定，不在执行点决定。**
建模论文的质量差距大半在"选了什么方法"。流程因此是
**探索 → 择优 → 深挖**，而不是线性推进，且允许携带证据回溯。

**P4 诚实性用验证保证，不用叮嘱保证。**
零数字通道、审计轨迹、交付评级这些硬资产是"约束后置"的成功先例——
不依赖模型自觉，依赖产物可验。本架构把这个经验推广到所有维度。

## 3. 总体架构

```
赛题 PDF + 数据附件
  │
  ▼
L0 能力画像                      src/probe/capability-profile.ts
  │  三探针（符号推理 / 执行正确性 / 结构合规）→ 档位 S / A / B
  │  档位决定：门禁初始强度 + 教学前置量。**不加分支，加一个自适应参数。**
  ▼
L1 环境装配                      src/knowledge/constitution.ts
  │                              src/knowledge/skill-library.ts
  │  prompt 内 = 最小宪法（容器 schema + 十条铁律 + 技能库索引）
  │  工作区 skills/ = 7 份可查询知识文档（运行开始落盘）
  ▼
L2 自由产出（探索—择优—深挖）    src/produce/explore-deepen.ts
  │  每问 2–3 个方案草图 → 四维打分择优 → 深挖；根本性失败可携带证据回溯
  │  这一层**故意不约束**——它是上限的来源
  ▼
L3 双通道证据                    src/verification/symbolic-channel.ts
  │  数值通道：code → jsonPath → Result → 正文（零数字通道，原有资产）
  │  符号通道：claims/*.py 断言脚本 → 执行通过 → 证据级别标注
  ▼
L4 语义校验                      src/verification/semantic-fingerprint.ts
  │  结构指纹 structHashOf（方程+假设+方法+参数+符号）
  │  三通道复验：数值 ∨ 结构 ∨ 评审重打分
  ▼
L5 对抗评审                      src/verification/adversarial-review.ts
  │  三个 persona 独立上下文盲评（数学严格性 / 应用相关性 / 写作与呈现）
  │  只看产物 + 评分细则，不看模型的自我声明（防共谋）
  ▼
L6 渐进约束与闭环                src/delivery/gate-state.ts
  │                              src/delivery/finding.ts
  │                              src/delivery/closure.ts
  │                              src/delivery/delivery-ladder.ts
  │  门禁状态机 DORMANT → WARN（微教学）→ ENFORCE（硬拦截）
  │  findings 分派 → 修复 → 复验（指纹）→ 消解；预算耗尽 = ESCALATE
  ▼
交付：CLEAN / MARKED / DEGRADED / ESCALATE 四档
      + 已知缺陷表（未消解项对用户可见）
```

## 4. 逐层详设

### 4.1 L0 能力画像

| 项 | 内容 |
|---|---|
| **文件** | `packages/paper/paper-foundation/src/probe/capability-profile.ts` |
| **承接功能** | 跑一次三探针（约 1–2 分钟），产出档位 S/A/B |
| **契约** | `assessCapability(observations) → CapabilityProfile`；`profileForTier` / `defaultProfile` 供无探针时使用 |
| **判档判据（预先声明）** | 三探针全过 → S；`structure` 过 + 至少一个别的过 → A；其余 → B |
| **为什么 `structure` 权重高** | 它是**架构的硬依赖**：容器不合规则整条生产链拿不到任何产物。`symbolic`/`execution` 不过只影响深度，不影响存活 |
| **无探针时的默认** | **A**（不是 S）。在零证据下假定模型不需要脚手架，会让弱模型直接卡在容器层（零产物），那比多给一点帮助贵得多 |
| **负反馈** | `withNegativeFeedback(tier, tightenedGates)`：上次被收紧过的维度，本次把档位调高 |

**对建模的影响**：间接。它决定模型拿到多少脚手架，不决定模型用什么方法。

**失败语义**：探针跑不起来 → 按 `defaultProfile` 取 A 档，并在审计里如实记录原因。
**绝不因为探针失败而拒绝运行。**

**审计钩子**
- [ ] 审计轨迹里有 `capability_check` 事件，且带 `tier` 与 `rationale`？
- [ ] `rationale` 说清了哪几个探针决定档位？（不可复核的判档等于没判）

**已接线**：`paper-shell probe` 跑三个可机械判定的任务并产出档位；`--capability-tier`
或 `PAPER_CAPABILITY_TIER` 把结果带进运行。三个判据都是机器判的（容器首键合规 /
代码真跑一遍 / 解析解在容差内），因此探针本身可回归。

**未验证项**：档位阈值（什么算 S / A / B）目前是**设计选择**，不是从数据反推的。
它需要真实运行的违规分布来校准——那正是上限测试该采集的东西。

### 4.2 L1 环境装配与知识外置

| 项 | 内容 |
|---|---|
| **文件** | `src/knowledge/constitution.ts`、`src/knowledge/skill-library.ts`、`src/knowledge/skills/*` |
| **承接功能** | 组装 prompt 内的最小宪法；把技能库落盘到工作区 |

| 文档 | 读它当 |

**对建模的影响：🟢 正面**
把模型的注意力预算从"读规范"释放回"想问题"。省下的部分本来可以用在建模上。

**失败语义**

| 情形 | 语义 |

| 技能库落盘失败 | 记 finding，运行继续（索引仍能告诉模型"应该有什么"，只是读不到） |

**审计钩子**

**已接线**：运行开始把 7 份文档落到 `<runRoot>/skills/`（幂等，同内容重写不改字节），
审计记 `skill_library_materialized`。

**未验证项**：模型**实际会不会去读**技能库，需要真实运行观测。
索引里写了"什么时候读"，但"模型读不读"是一个行为问题，不是机制问题——它是上限测试

### 4.3 L2 探索—择优—深挖

| 项 | 内容 |
|---|---|
| **文件** | `src/produce/explore-deepen.ts` |
| **承接功能** | 强制"先比较再深挖"，并给出带回溯的失败出口 |
| **契约** | `ExploreSelectDeepenSession`：`submitSketches` → `beginSelection` → `recordSelection` → `backtrack` |
| **预算** | 探索段约占总预算 **15%**（设计选择，非测量结论） |
| **数量约束** | 每问 2–3 个草图（少于 2 没有比较，多于 3 是浪费） |

**为什么不是线性流程**
线性流程里的模型在深挖阶段发现方法不适配时只有两个选择：硬着头皮产出错的
结果，或者编造成功。两者都是灾难。回溯给了第三条路——**这是诚实性与上限的
双重保障**。

**回溯必须有证据**：`failureEvidence` 少于 16 字符即拒绝。"结果不好看"不是
回溯理由，那是另一种不诚实。

**对建模的影响：🟢🟢 全架构中最正面的一层**
方法选择从**一次性赌注**变成**可回溯的决策**。

**模型能否被准确约束**
**故意不约束。** `method` 是自由文本；打分四维是**建议**不是白名单。
任何把候选方法收成枚举的做法都会把刚解开的封顶重新焊回去。

**失败语义**

| 情形 | 语义 |
|---|---|
| 草图不足 2 个 | 拒绝该次提交（结构上不允许"没比较就深挖"） |
| 择优无理由 / 落选无理由 | 拒绝 |
| 回溯无证据 | 拒绝 |

**审计钩子**
- [ ] `decision.md` 是否落盘？（择优过程从隐性变显性）
- [ ] 落选方案是否在 `explore/archive/`？（不删才可复活）
- [ ] 回溯事件是否带失败证据？

**未验证项**：`[设计D]` 的三段流程**尚未接进 executor 的节点序列**——模块与
不变量已就位并有测试，接线属于实施顺序 P1 项。

### 4.4 L3 双通道证据

| 项 | 内容 |
|---|---|
| **文件** | `src/verification/symbolic-channel.ts`（新增）；零数字通道为原有资产 |
| **承接功能** | 让解析推导获得与数值结果同等的可信地位 |
| **契约** | `registerSymbolicClaim(rootDir, {claim_id, script, statement})` → `SymbolicClaim` |
| **证据级别** | `symbolic_proof`（代数确证）/ `sampling_evidence`（有限点抽样） |

**级别由通道标注，不由模型自称**：`classifyEvidenceLevel(scriptText)` 看脚本
**实际用了什么**（`checkodesol`/`limit`/`simplify(...) == 0` → 代数确证；
`all(... for ... in range/linspace)` → 抽样）。两者都有时取**较低**级别。

**措辞纪律是机械检查的**：`assertWordingMatchesLevel(level, wording)` ——
抽样级别的 claim，引用处不得含"证明/恒成立/严格成立"。
把抽样证据说成"证明"是比数字算错更严重的诚实性问题。

**对建模的影响：🟢 正面**
上限最高的那类能力（理论分析）第一次有了合规的表达通道。

**模型能否被准确约束**
❌ 不在 decode 期约束；它给的是**表达通道 + 级别标注**，不是约束。

**失败语义**

| 情形 | 语义 |
|---|---|
| 断言失败 | 该解析结论**不得进论文** |
| 脚本跑不起来（依赖缺失/语法错/超时） | `unverifiable`，**与"未通过"同级**（C3）——未执行不是中性状态 |

**审计钩子**
- [ ] 断言脚本目录 `claims/` 是否落盘？
- [ ] 交付附录的"符号证据登记"是否列出了每条 claim 的级别？
- [ ] 有没有把 `sampling_evidence` 说成"证明"的句子？（可机械检出）

**未验证项**：`[现状A]` 同族的 `v7-sympy.ts` 早已存在但**孤立未接线**；
本模块把它提升为带级别的通道。端到端接线属于 P1 项。

### 4.5 L4 语义校验与三通道复验

| 项 | 内容 |
|---|---|
| **文件** | `src/verification/semantic-fingerprint.ts` |
| **承接功能** | 让**语义类修复**在复验里可见 |
| **契约** | `structHashOf(structure)` · `threeChannelVerdict(input)` |
| **结构指纹覆盖** | 方程（规范化表达式）+ 假设 id 集 + 方法族 + 参数签名 + 符号表 |

**为什么单靠数值指纹不够**
若指纹只覆盖数值，那么"换方法、增删方程、调整假设"在指纹上**看起来毫无变化**
——修复被误判为"没修"。这是复验在建模层的**半盲**。

**修法不是换判据，是加通道**：

```
修复成立 ⟺ 数值指纹变化   （覆盖数值类修复）
         ∨ 结构指纹变化   （覆盖语义类修复）
         ∨ 评审重打分达标 （覆盖呈现类修复）
```

三条取**或**。这条设计的价值在于：**它让"改文字去迎合旧数字"不再能伪装成修复**
——那种改动三条通道全不动，一致判"未修"。

**规范化只去排版差异**（空白、`$`、`\left`/`\cdot`、大小写），**不动任何符号或数字**。
稳定性要求：同一份模型必然得到同一指纹，否则复验会把"没改"判成"改了"——
那是假阴性，比漏报更伤闭环的可信度。

**对建模的影响：🟢 正面**
它使"修复是否真的发生了"这个问题在建模层变得可回答。

**失败语义**：`repaired === false` 的语义是"**未修复**"，不是"检查失败"。
调用方必须推回闭环（重试或消解），**不许沉默通过**（C1）。

**审计钩子**
- [ ] 复验是否记录了三条通道各自的证据（而不是一个布尔）？
- [ ] 结构指纹是否对排版差异稳定？（测试里有负对照）

**未验证项**：三通道里的**评审重打分通道**尚未接线（需要评审循环产出分数）。
数值与结构两条通道已可用。

### 4.6 L5 对抗评审

| 项 | 内容 |
|---|---|
| **文件** | `src/verification/adversarial-review.ts`（包装原有的 `v5-adversarial.ts`） |
| **承接功能** | 三个独立视角检出缺陷，产出 findings 交闭环 |
| **契约** | `adjudicateThreePersonaReview({findings, paperText, refResolves})` → `AdversarialReviewOutcome` |
| **三个 persona** | 数学严格性 / 应用相关性 / 写作与呈现 |

**为什么是三个而不是一个"总评审"**
论文的失败模式至少三类且**互不覆盖**：推导错（数学）、没回答题目所问（应用）、
章节缺要素（呈现）。一个"总评审"会系统性偏向它最容易判的那类，另外两类静默漏过。

**盲评（防共谋）**：每个 persona 只看**产物 + 评分细则**，不看模型的自我声明。
实测中出现过"复核与答题同源、读同一份输入、上游读错则共犯同一错误"的形态；
把自我声明从评审输入里摘掉是这条链上唯一能做的隔离。

**误报优先于漏报**：LLM judge 会被自信行文诱导出很高的假阳率，而塞满误报的
findings 队列会**淹掉闭环**。取向是宁可少报。

**引用悬空 / span 伪造的条目被丢弃**——幻觉攻击不算发现，但**丢弃记录进审计**。

**审计钩子**
- [ ] 三个视角各自是否**真的攻击了**？（某视角零发现 → `complete=false`，不能读作"该维度无问题"）
- [ ] 被丢弃的条目是否可见？

**未验证项**：三个 persona 的**实际 prompt 尚未接线**（裁决逻辑与契约已就位）。

### 4.7 L6 渐进约束与闭环

这一层是本次改造**唯一真正新增**的东西，也是两侧都缺的那一半。

#### 4.7.1 门禁状态机

| 项 | 内容 |
|---|---|
| **文件** | `src/delivery/gate-state.ts` |
| **状态** | `DORMANT`（只记录）→ `WARN`（注入微教学）→ `ENFORCE`（硬拦截） |
| **登记表** | `GATE_ACTIVATIONS`：每个门禁登记 `home`（interface/knowledge）+ `microTeaching` + 三档初始模式 |

**关键性质**
- **未登记的门禁默认 ENFORCE**——登记表是白名单，不是黑名单。一个忘了登记的门禁
  不该因为"忘了"而被静默放过。
- **运行内不衰减**——"再试几次就过了"不是一条可行路径。跨运行的档位调整走 L0。
- **一套代码两种行为**：S 档的绝大多数门禁永远停在 DORMANT；B 档在关键维度上
  自动收紧到与旧形态同等的严格度。

#### 4.7.2 finding 契约

| 项 | 内容 |
|---|---|
| **文件** | `src/delivery/finding.ts` |
| **字段** | `id / category / severity / checker / where{files, artifactScope} / evidence / fingerprint / fixHint / state / attempts` |
| **终态** | `fixed / accepted / rejected / unverifiable`（**没有"未处理"这个终态**） |

**每个字段都有下游消费者**，没有消费者的字段不该存在：

| 字段 | 消费者 | 缺了会怎样 |
|---|---|---|
| `checker` | 闭环复验（重跑**同一个**） | 无法做 fingerprint 比对 |
| `where.artifactScope` | 闭环分派 | 无法决定谁修，会退回"改文字" |
| `fingerprint` | 闭环复验 | 无法判断"是否真的修了" |
| `fixHint` | 修复者 | 修复质量下降 |
| `state`/`attempts` | 闭环预算 | 无法防震荡 |

**分派表（对抗成本不对称）**——这张表存在的理由是一个实测事实：一次真实修复
**只碰了论文正文**，因为改文字比重跑代码便宜得多。架构若不明文规定分派规则，
它就总会选便宜的那条。

| finding 落在哪 | 分派给谁 | 禁止 |
|---|---|---|
| `code/*.py` | 代码技能（重跑） | ❌ 改写论文里的数字来"对齐" |
| `results/*` | 重跑产出脚本 | ❌ 文本编辑该文件 |
| `figures/*` | 重绘 | ❌ 改数据源来迁就旧图 |
| `paper/*` | 写作技能 | ✅ 允许直接编辑 |

#### 4.7.3 闭环协议

| 项 | 内容 |
|---|---|
| **文件** | `src/delivery/closure.ts` |
| **状态机** | `open` → 分派 → 修复 → **复验（重跑同一 checker，比对 fingerprint）** → 消解 |
| **预算** | `{maxRounds: 2, maxAttemptsPerFinding: 2}` |
| **终局** | `CLEAN` / `MARKED` / `ESCALATE` |

**四条硬约束**（每条都是代码里的断言，不是文档里的倡议）：

| # | 约束 | 常量 | 对应的实测失败 |
|---|---|---|---|
| **C1** | 交付前必须复验 fingerprint，不接受"我改过了" | `C1_FINGERPRINT_RECHECK_REQUIRED` | 一份运行的修复清单逐条真实落地（抽验 5/5）却**无人复评**；另一份的"改进轮"是**空操作**（round0 与 round1 字节完全相同） |
| **C2** | 预算耗尽的语义是 `ESCALATE`，**不是** `CLEAN` | `C2_BUDGET_EXHAUSTED_IS_ESCALATE` | 一份运行在 `{"status":"in_progress"}` 状态下**交付了**——不是"判定通过"，是"没跑完就交了" |
| **C3** | checker 未执行与未通过**同级** | `C3_NOT_EXECUTED_EQUALS_NOT_PASSED` | 一份运行的数据门禁停在 `🔄 待自检`（未执行）而交付照常；另一份的通过条件是**被检查者自己写进产物的字符串** |
| **C4** | checker 的检查面 = 交付物**全集** | — | 交付 JSON 里的陈旧值（与正文差 6.6 倍）逃过一切门禁，因为门禁只查 `paper/main.md` |

**显式接受是一等公民**：修不掉的东西写进交付物附录的**已知缺陷表**，而不是消失。
这解决了两个方向的失败——"检测到但无消费方"与"findings 一律拒绝（零产物）"。

#### 4.7.4 四档交付语义

| 项 | 内容 |
|---|---|
| **文件** | `src/delivery/delivery-ladder.ts` |
| **档位** | `CLEAN` / `MARKED` / `DEGRADED` / `ESCALATE` |

| 档位 | 触发 | 交付物形态 | 用户动作 |
|---|---|---|---|
| `CLEAN` | findings 空 | 完整包 | 直接交 |
| `MARKED` | findings 非空但**全部已消解/接受** | 完整包 + 已知缺陷表 | 看一眼附录 |
| `DEGRADED` | 兜底路径产出，或**没有任何可执行证据** | 结构完整 + 注明"未经规范核验" | 需人工补 |
| `ESCALATE` | 闭环预算耗尽 / 兜底也不适用 | **未完成包**：中间物 + 缺口清单 + 建议动作 | 人工接管 |

**唯一真正的硬拒绝**：连"未完成包"都产不出（正文为空）。
**唯一保留的 finding 级硬阻断**：`fabricated_reference`（编造参考文献）——
在期刊场景下它直接构成学术不端，值得硬阻断。

**两个致命条件接上了真实判定**（此前它们被**写死为 false**，于是文档承诺的
三个致命条件实际只有"空内容"可达——"退化为 MARKED 的保护伞有三根伞骨是画上去的"）：

- `executionFailed`：链路上声明了执行，却一个 Result 都没铸出来 → 现在是
  DEGRADED 的**证据**，不是硬拒绝（"代码没跑成"应当交出一份标注清楚的草稿）。
- `referenceCatastrophe`：IR 里**有** claim 声称绑定了 Result，但那些 Result
  一个都不存在 → 硬拒绝。这与"根本没有证据"是两件事，必须分开：
  前者是"声称有支撑而实际没有"，后者是"一份草稿"。

**交付物顶部有一句话状态**（`renderTierBanner`）：一份带未消解缺陷的交付物，
头部**不能**显示"通过"。

**审计钩子**
- [ ] 审计轨迹里有 `closure_closed`，带每条 finding 的终态与复验记录？
- [ ] 审计轨迹里有 `gate_state_changed`，带本次运行的模式与违规计数？
- [ ] 交付物附录里有没有"已知缺陷表"？
- [ ] `ESCALATE` 时是否产出了"未完成包"而不是空手而归？
- [ ] 是否存在"只有一份 verdict、无第二次评审"的路径？

**未验证项**：闭环的**自动返修执行者**目前只覆盖**格式层**
（`src/delivery/auto-repair.ts`，走 `applySafeFormatFixes` + N30 不变量）。
建模层的返修需要重跑代码/重出图/重写章节，属于 P2 项——在那之前，
建模类 finding 走"显式接受"并如实写进已知缺陷表，**不假装修过**。

## 5. 横向机制

### 5.1 默认档位的方向性反转

`deliveryGradeMode` 的默认值从 `strict-tolerance` 改为 **`fail-soft`**
（`apps/paper-shell/src/cli.ts`、`src/executor-service.ts`）。

**理由**：`strict-tolerance`（任何 finding 即 `BLOCKED`、零产物）是一条
**从未在任何真实产出中被验证过**的路径——所有真实交付都来自"报告 + 放行"
那条路径。阻断路径缺乏实证基础，而放行路径的缺陷（finding 无归宿）已由 L6 补上。

三档仍然都在，`strict-tolerance` 需显式开启（`--strict-tolerance`）。

### 5.2 失败语义阶梯替代布尔式 BLOCKED

旧形态是 `gradeInput.length === 0 ? 'CLEAN' : 'BLOCKED'`，且注释明写
`never MARKED`。于是输出分布是**双峰**的：要么核验通过，要么零产物，
**没有"平庸但可用"这一档**——而中间档恰恰是优质论文实际诞生的地方。
一条从未产出过"合格稿"的产线，没有资格谈优质稿。

### 5.3 预算与超时

| 预算 | 归属 | 耗尽语义 |
|---|---|---|
| token / USD | 声明方 | `ESCALATE` |
| 闭环轮次 | `closureBudget` | `ESCALATE`（**不可配置成 CLEAN**） |
| wall time | 声明方 | `ESCALATE` + 保留中间物 |

## 8. 判据边界与未验证项

**必须说清的四件事**：

1. **本架构的机制已落地并有测试（1594 个测试全绿），但"上限提升"是推论，不是实测。**
   已实测的是：默认档位反转后，此前会被判 `BLOCKED` 的运行现在产出标注交付物；
   闭环的不变量（C1/C2/C3、ESCALATE 语义、分派表）有机械落点。
   **未实测的是：放开约束后论文质量是否真的提升。** 那需要真实运行数据。

2. **L0/L2/L3/L5 已全部接线并有主线验收测试**（`tests/architecture/wired-into-mainline.spec.ts`
   从节点标题、prompt 内容与审计事件取证，而不是直接调模块——直接调模块只能证明
   模块本身能跑）。**仍未接线的只有两项**：建模层的自动**返修执行者**，与随之而来的
   评审重打分通道（见 §7 的 P2）。

3. **`PAPER_CONSTITUTION` 仍是 16K 字符量级**，不是设计稿里说的"200 行"。
   原因诚实记账：宪法的主体是**容器 schema**，那部分不可压缩（模型看不到就产不出
   合法容器）；真正可压缩的是**知识**，它已经全部外置（由
   `constitution-contract.spec.ts` 的"知识类措辞不得出现在宪法里"逐条钉住）。
   **把 schema 也搬走不是目标**——那只会让容器产不出来。

4. **闭环的建模层返修尚不存在**。当前的诚实做法是"显式接受 + 已知缺陷表"，
   而不是假装修过。这是**已知的、有意的**缺口，不是遗漏。

### 8.1 第一轮上限测试（2024B × deepseek-v4-pro）的实测校正

> 完整报告：`artifacts/upper-bound/ROUND-1-REPORT.md`。这一节只记**改变了本设计判断**的部分。

**① F1 已在真实运行上成立。** `strict` 与 `fast` 两次运行的 E2 都七次全败，但两次都
交付了完整包（`DEGRADED` + 已知缺陷表）。旧形态下这两次都是 `BLOCKED` / 零产物。

**② 瓶颈不在评审，在 E2。** 两次运行的 14 次拒绝里，**71% 追溯到同一个根因**：
`reference_scope_mismatch` —— **IR 的 scope 模型无法表达"全局假设"**。模型在 E1 里
正确识别出"次品事件独立"是全局假设、声明一条并跨子问题引用，被 `REF-003` 拒绝。
**这是契约缺一个表达能力，不是模型错。**

> **已修（第二轮实测验证）**：给 `AssumptionSpec` / `EquationSpec` 加可选字段
> `shared: boolean`——作用域仍指向它推导自的子问题（保持溯源），但声明 `shared: true`
> 后**任何**子问题的模型都可引用它（`ir/contract-objects.ts` +
> `ir/refs.ts` 的 `validateScopeOwnership`）。**不变量未被削弱**：没声明 `shared` 的
> 跨作用域引用照旧拒绝（有负对照测试）。宪法与 `skills/paper-contract.md` 同步改成教
> 这个机制，并明确否掉"抄成四份不同 id"的记账式绕法。
>
> **修复效果（strict 同题同模型对照）**：`REF-003` 从 **7/14 → 0/8**；失败整体下移到
> 生产链（0 → 4 次），即容器被准入、链真的跑起来了；token 反而少烧 18%
> （213,797 → 175,219）。详见 `artifacts/upper-bound/ROUND-2-REPORT.md`。
>
> **瓶颈因此改变**：从"契约缺一个表达能力"变成"**模型自己的声明有瑕疵**"
> （`S_P1` vs `S-P0` 的命名不一致、结论缺 quantity_ref、章节要素不全）——而后者是
> **可以被教好的**。三条规则都已在宪法或技能库里，于是下一轮的核心待测问题变成：
> **模型读不读技能库？**

**③ 多视角评审的价值当前**无法测量**。** `strict` 用 1.6× token 换来 12 次评审，
交付档位与 `fast`（2 次评审）相同——**因为链没走通，评审的对象是一份兜底稿**。
因此本设计 §4.6 对"三视角优于单视角"的论证，在 E2 通了之前**没有实测支持**，
只有机制层面的理由。这是一个必须记下的负面结论。

**④ L3/L4 在两次运行中**未被触发**。** 它们挂在交付链上，而 E2 未过。
**这不是接线失败，是没走到**——需要 E2 先通。

**⑤ L0 探针的判据被实测校准。** 探针结果：`structure` ✅ / `execution` ✅ /
`symbolic` ❌（五次采样 69.7 / 69.7 / 69.5 / 68.5 / 49.6，正确值 68.5）。
**模型能写出跑对的代码，但同样的算术在脑子里算就不可靠**——这从反面论证了零数字
通道与符号通道的存在理由。

### 8.2 第三轮实测：知识投递方式与封顶移除

> 完整报告：`artifacts/upper-bound/ROUND-3-REPORT.md`。

**① 知识投递：从"指路"改为"内联"。** 第一版 L1 写"必读 `skills/x.md`，用 `read_file`
读它"——而**本管线的模型调用没有工具**（`streamCompletion` 不发 `tools`，没有 tool 循环）。
那是一条**无法被遵守的指令**。改法：每一步的简报把它需要的知识**内联**进那一步的 prompt
（放在最后），字段按参考实现的形态补齐（目标产物 / 上游状态 / 本步知识 / 本步定位 /
**不要做** / **完成标志**）。代价可控——每步只内联自己需要的 1–2 份（分析 0.3KB、
评审 2.1KB、产出 10.3KB）。

**② 闭集契约仍在，且模型正在照它选方法。** CLI 注入的横幅原文是
`候选模型集(封闭,只能从中选择,禁止自创)`，一次真实运行的 E1 **逐字照抄**了它。
**这是全案最要命的一处封顶**——本架构的立论是"质量差距大半在选了什么方法"。
已改为**软先验**（"这不是白名单…不对方法选择施加约束"）；路由失败从 `return 3`
（零 token 拒绝）改为 `F5-other` 标注继续；族验证规则从"候选模型封闭"改为
"选型已登记"。

**③ 效果必须分开说：行为变了，交付物没变好。** strict-3 的 E1 从候选清单里挑
weighted-sum；strict-4 的 E1 写"整体方法族为 F4，**但问题 1 本质上是 F3 的边界**…
采用统计检验 + 期望成本递推 + 策略枚举的**混合框架**"——**模型跨出了那个族**。
但交付档位四轮都是 `DEGRADED`：**链从未走通过一次**。方法自由让模型想得更好，
而"想得更好"要变成"交付得更好"，得先让 E2 → 生产链走通。

**④ 下一步的信息量在"通链"，不在"加层"。** 四轮下来交付档位没动过。最高频且
机械可判的两类失败（`physical key 'S_P1'` 不解析 ×4、容器 `entries` 形状 ×4）
应当做成**产出前的自检**，而不是再写一条教学。

**未验证项清单**：

| # | 项 | 需要的验证方式 |
|---|---|---|
| 1 | 模型会不会真的去读 `skills/` | 真实运行观测查询行为 |
| 0 | 三视角评审在真实模型上是否真的产生**不同**的缺陷（而不是三次重复同一句） | 真实运行的缺陷分布 |
| 2 | 放开 L2 约束是否放大错误空间 | 分档 A/B 测试（需先有闭环度量） |
| 3 | 门禁状态机的档位阈值是否合适 | 真实运行的违规分布 |
| 4 | 探针能否稳定区分 S/A/B | 用历史运行数据回测 |
| 5 | 符号通道的证据级别判定是否会误判 | 收集真实 `claims/*.py` 语料 |

**关于"分档测试"的依赖关系（重要）**：
要测"放开多少合适"，判据必须是"放开后数字还可回溯吗、评审 major 变多还是变少"
——而这两个判据的采集**本身就是 L6 的工作**。
**先建度量，再做实验**：L6 未建成之前做分档测试，得到的只会是一份自称完成的散文。

### 8.3 第四轮实测：从"内联知识"推进到"可执行检查"

> 完整报告：`artifacts/upper-bound/ROUND-4-REPORT.md`、`ROUND-5-REPORT.md`。

**① 内联知识解决了"读不到"，没解决"不会照做"。** 第三轮把知识内联进每步简报之后，
模型确实拿到了全部规则（它们就在 prompt 里）。但 strict-5/strict-7 仍然在**自己声明的
自相矛盾**上翻车：配置键指向没声明的符号、`entries` 写成空数组、图注里写了数字。

这些**都不是知识不足**——规则就在上文几百字处。它们是**执行时的粗心**。于是第四轮
在提交前加了一段"请自查这六条"的 prompt 自检。**结果：strict-7 里那两类失败一次没少。**

→ 结论与第三轮同源，只是更硬：**模型不会因为被告知就照做。**

**② 修法：把判据做成工具，而不是一段请求。** L1 因此从"内联知识"推进到"可执行检查"：

| 项 | 内容 |
|---|---|
| **文件** | `src/produce/self-check.ts`（判据）· `src/executor.ts#callWithSelfCheck`（工具回路）· `apps/paper-shell/src/real-provider.ts`（wire 边界） |
| **工具** | `check_container`，**只读**、唯一一个 |
| **判据** | 复用 `parseModelContainer` 等**真实准入路径**，不另写一份——工具看到的第一个问题就是准入时会拒的第一个问题 |
| **轮次上限** | 3 次工具调用；到顶后下发"给最终答案、不要再调用"，并**再取一次**（上限不是新的门） |
| **审计** | `ir_entry_written:E2SelfCheck`，带 `calls` 计数 |

**工具"判不了什么"必须自己说出来。** `SelfCheckVerdict.notChecked` 如实列出三类
运行期才知道的东西（`numeric_config.json` 的键、`jsonPath` 是否解析到有限数、
章节篇幅）。缺了这一项，"检查过了"会被读成"全对"——那比没有工具更糟。

**③ 接线上抓到的一个静默失效（本轮最有价值的一条）。** executor 早就会发出
`tools: [check_container]`，`real-provider.ts` 也早就把它转成 wire 形状。但**中间的
接缝**（`cli.ts` 的 `adapterStream`）的类型是

```
adapter: (r, req: { system?: string; messages: Array<{content: string}> }) => …
```

——一个**装不下 `tools` 的类型**。它把请求重建成 `{system, messages}` 再转交，工具
定义就此消失；同样的原因，`tool-result` 内容块也被拍平成空串。

后果全是**静默**的：请求照样 200，模型只是永远没有工具可调。于是"模型不爱用工具"
与"工具根本没送到"在事后**无法分辨**——而审计里连一条 `E2SelfCheck` 都不会有。

这与本项目反复抓到的那类缺陷同源：**判定侧写了，传递侧没写**。修法除了补齐三处
（接缝类型、`seamTextOf` 的 `tool-result` 分支、cassette 指纹里的 `tools`），还加了
一条**结构性不变量测试** `apps/paper-shell/tests/seam-forwards-tools.spec.ts`——
它静态断言"接缝的请求类型装得下 tools、`adapterStream` 真的转交、工具结果不被拍平"。

**④ cassette 指纹必须含 `tools`。** 带工具与不带工具是**不同的请求**（模型能做什么
不一样）。不进指纹的话，一份"没工具"的记录会被当成"带工具"的请求的回放来源——
那是假回放。这与"过期 cassette 必须被拒，不得静默匹配"是同一条纪律。

**⑤ 实测结果：工具会被用，但没让 E2 通过。**（strict-9，2024B × deepseek-v4-pro）

- **模型确实调用它**：`E2SelfCheck calls=3` ×2 与 `calls=1` ×1——**用满额度**。
  第四轮留下的问题（"模型会不会去用工具"）答案是"会"。
- **链走得更远**：`RunArtifact` / `Result` / `Claim` / `ExecutionRecord` /
  `FigureSpec` 全部出现（`minted_ir_count` 77），生产链**第一次跑到解释层**；
  `docx` 致命项 2 → 1（未填充占位 8 → 0）。
- **但交付档位仍是 `DEGRADED`**，路径仍是 `B-e1-direct`。**五轮连续如此。**
- **成本翻近 3 倍**：583K/349K tokens（vs 204K/94K）。工具回路每轮重发完整对话。

**⑥ 实测暴露的缺口：工具报过，模型没改。** 审计里 `E2SelfCheck calls=3` 与
`E1_E2_FIDELITY_VIOLATION` **相隔 42 毫秒**——工具跑完了，紧接着提交的容器里
那些问题一个都没改。这不是"没送到"，也不是"查不出来"，而是**额度用完后
工具说过的话随这一轮一起丢掉了**。

两处修法（都**不**把工具变成门）：结论进审计（`E2SelfCheckCall` 带
`admissible` / `problem_count` / 前 3 条 `problems`），以及结论**带过这一轮**
（最后一次结论为"不可准入"时追加进下一次尝试的回灌，code `SELF_CHECK_REPORTED`）。

**未验证项（本节新增）**：

|---|---|---|
| 6 | ~~模型会不会调用 `check_container`~~ | ✅ 已验证：会，且用满额度 |
| 7 | 调用了之后那两类机械失败是否减少 | ✅ **容器级失败清零**（strict-11 的 `container_refused` = 0） |

**⑦ 判据前移的效果（strict-9 → strict-10 → strict-11）。** 三次真实运行正好是
自检工具从"没有"到"有"、判据从"少"到"全"的过程：

| 运行 | 容器级拒绝 | 产出链拒绝 | docx | minted IR | tokens (in/out) |
|---|---|---|---|---|---|
| strict-9 | 5 | 1 | ❌ | 77 | 583K / 349K |
| strict-10 | 6 | 0 | ❌ | 70 | 244K / 194K |
| strict-11 | **0** | **5** | **✅** | **138** | 836K / 454K |
| strict-12 | 1 | 1 | ✅ | 10 | 365K / 255K |
| strict-13 | **0** | **6** | ❌ | **174** | 889K / 454K |

**瓶颈换了地方**：不再是"容器写不对"，而是"论文正文的质量不达标"
（参考文献要指向实际用过的方法、图注不许出现游离数字）。这两条都是**内容**判据，
**在容器里看不出来**——它们属于 L5 评审与产出链自己的判据，不该由容器级工具承担。

**⑦b 工具回路的终止条件（strict-12 实测）。** 把额度从 3 提到 6 之后，模型不是
收敛而是**震荡**：第 3 轮工具已判"可准入"，第 4 轮它又把容器改坏，最后提交了一份
连 JSON 都不合法的文本。**所以缺的不是额度，是终止条件**——工具说"可准入"就是目标
状态，到达即停。修法：批准后立刻要求模型把那份文本**原样**给出并取走，不再执行任何
工具（准入判定一个字没变，改的只是循环何时结束）。

**⑦c 收口之后的 strict-13：一条规则卡住整条链。** 批准即收口上线后，
`container_refused` 仍为 **0**，工具 10 次调用里 5 次判"可准入"，`minted_ir_count = 174`
（本架构最高）。而 7 次拒绝里 **4 次是同一条**：

```
figure caption/axis label contains numeric literal '2' that is not a referenced Result value
```

游离字面量每次都是 `2`——模型写的是"问题2 / 情形2 / 图2"。

**这不是模型的缺陷，是措辞的缺陷。** 规则早就在宪法里，但那条措辞对**中文写作者**
不起作用：没人会把"问题2"里的 `2` 读成"数字字面量"。修法是**改措辞，不改判据**——
点名陷阱（`CHINESE ORDINALS ARE THE TRAP`）并给出合法改写（"问题二"，或更好：直接命名
"抽样检验方案 / 生产决策"）。测试里加了方向性守卫：**原禁令必须逐字保留**。

这正是 W8.11-A1 教过的：**只加禁令不加理由，模型会换一种方式违反。**

**⑧ 当前最大的一处成本浪费。** 产出链在 EXECUTE 节点内运行，它拒绝时整个节点重试，
于是**再花一次完整的 E2 调用**（40KB 输出、数分钟）。strict-11 用了 836K/454K tokens。
产出链的返修对象是**正文与图注**，根本不需要重新声明整个容器——这是唯一一处
"重试的东西与失败的东西不是同一个"的地方，也是下一步的第一优先。
