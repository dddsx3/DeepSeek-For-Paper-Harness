# 「阶段内提醒者 / 审计员」角色调研评估

> **编制**：2026-10-27。**性质**：调研件——**未做任何代码改动，等待裁决**。
> **范围界定**（按用户口径）：只评估"在阶段工作当中提醒模型不要犯错"的角色，
> **不含**每阶段结束签发通行证的机械门禁（那是 `stages/gates.ts` 的职责，另论）。

## 0. 先厘清：代码里其实有三层防错机制，用户问的是哪一层

| 层 | 谁在做 | 何时 | 是不是"提醒" |
|---|---|---|---|
| **L1 静态自检清单** | 简报里的 `selfCheck`（18 处，逐阶段不同） | 阶段开始时一次性给出 | 是"事前提醒"，但是**死的**——写进提示词后模型看不看靠自觉 |
| **L2 失败回灌** | runner 在重跑时把上一轮的四类失败拼进简报开头 | 每次重跑开始 | 是"事后提醒"——**唯一真正带上下文的提醒** |
| **L3 逐节点审计** | 独立模型角色（`stages/audit.ts`），评分+findings | 阶段末、机械门禁之后 | 是"判官"，**不是提醒者**——它的产出要么拦下本阶段，要么只留档 |
| （排除）机械门禁 | 确定性代码 | 阶段末 | 签发通行证，不在本调研范围 |

**结论先行**：用户描述的那个"在每一阶段工作中提醒模型不要犯错的角色"，在当前实现里
**并不存在一个独立实体**。存在的是：L1 静态清单 + L2 上一轮失败回灌 + L3 阶段末审计。
L3 常常被误读成"提醒者"，但它的真实语义是**准入判定**；它唯一"提醒"的时刻，是它判 fail
之后、下一轮重跑开始时（经 L2 投递）。**这个区分是本调研最重要的发现。**

## 1. 当前设计的准确形态（代码证据）

### 1.1 L3 审计的契约
- **独立性**：提示词只含「任务陈述 + 产出契约 + 门禁 id + 上游文件名 + 题面事实」，
  **刻意不给执行者的提示词与推理**（`stages/audit.ts:18-21, 124-190`）。
- **结构化判定**：必须返回 JSON `{verdict, score, structure_ok, requirement_compliance[], findings[], missing[]}`；
  散文评价不被接受（`parseAuditVerdict`，`audit.ts:270`）。
- **机械阈值**：任一 `fatal` / `score < 0.7` / 结构不完整或 `missing` 非空 → 不放行
  （`decideAudit`，`audit.ts:95`）。
- **`2 ≠ 0` 纪律**：审计调用失败（配额/坏 JSON/空回答）记"无法判定"，进通行证
  `unverifiedGates`，**绝不当通过**（`runner.ts:790-810`）。
- **审计结论进通行证**：`StagePassport.audit`（`handoff.ts:85-90`）——成为交付物的一部分。
- **模型**：`PAPER_AUDIT_MODEL`，**默认与执行者同模型**，但全新上下文（`stage-service.ts:745-747`）。
- **成本**：11 个模型阶段 × 每次尝试 1 次额外调用（4 个确定性阶段跳过）。

### 1.2 L2 回灌（真正起"提醒"作用的部分）
重跑时拼四路：机械门禁失败 + 审计 findings + 复核结论 + 运行时失败
（`runner.ts:663-671`），渲染成简报的独立小节：
「上一轮审计提出的问题（**必须逐条处理或明确反驳**）」，逐条列 severity/位置/问题/建议改法，
并明说"沉默地重发一遍不算处理"（`briefing.ts` 的 `priorFindings` 渲染段）。

### 1.3 阶段链**没有**阶段内自检工具
`stage-service.ts:794`：`toolsMounted: () => false`。
即 13 阶段链里**不存在** `check_container` 这类"工作当中可调用"的检查工具——
那套工具回路只存在于旧的单发执行器（E1/E2）路径。**阶段内模型没有任何主动自检手段。**

## 2. 实证效果（本次 + 历史运行）

### 2.1 本次 2024B-mcgrox-1 的审计时间线（日志实测）

| 阶段 | 第一次 | 回灌后 | 审计抓到了什么（机械门禁抓不到的） |
|---|---|---|---|
| prob-analysis | **fail 0.60**（1 fatal） | **pass 0.85** | `CAPABILITY_CHECKLIST` 里 C-Q1-REJECT95 / C-Q1-ACCEPT90 两条 machine_check **概率方向写反且与 required_output 自相矛盾**——结构完全合法，机械门禁全绿 |
| modeling | pass 0.80（4 findings） | — | 非阻断观察 |
| code | **fail 0.30**（2 fatal） | 迭代中 | ① `RESULTS.md` 开篇自述"写作时尚未持有运行产物，任何数都是心算结果"——**零数字通道违规的自白**；② `code/results.json` / `outputs.json` 声明了却不在磁盘上 |

**这一组数据支持"审计有效"**：三条 fatal 全部属于"形态合法但语义错误"，正是机械门禁的盲区；
且 0.60→0.85 证明"回灌+重跑"闭环真的把问题修掉了（不是运气：fatal 的具体条目变了）。

### 2.2 设计者自己记录的失效模式（代码注释，非推测）

- **极性误判**（`audit.ts:109-116`）：审计员把"是否存在冲突"这类负面检查写成
  `requirement_compliance` 条目，note 写"未发现冲突"却给 `done:false` → 判成"一项要求未完成"，
  硬拦整阶段，代价"十几次模型调用"。已在提示词里立了"负面检查必须改写成正面句"的纪律。
- **假阴性**（`audit.ts:170-174`）：早期只给"上游文件名清单"、不给题面 → 审计员无从判
  "是否与题面相符"，漏掉 2024B 的真实致命缺陷（题面给了调换损失 `ce=40`，代码从头到尾没用它，
  "什么都不检查"虚假胜出，利润 104 vs 真值 66.09）。现已内联题面事实。

### 2.3 结构性缺口（本次调研新发现）

**通过审计的 non-blocking findings 没有归宿。**
`_audit.json` 的读取点全仓只有一处：`priorAuditFindings()`（`runner.ts:415`，只在**重跑时**用）。
`delivery/`、`executor.ts`、`handoff.ts` 均不读它（grep 实测零命中）。
后果：一个阶段"pass 0.80、4 条 findings"（本次 modeling 就是），这 4 条既不影响放行，
也**不进最终交付的已知缺陷表**——只躺在阶段目录与通行证里。
这直接违反项目自己的铁律"**检出到的每个问题都必须有归宿**（修掉 / 显式接受并写进已知缺陷表）"。

## 3. 与广泛验证设计的对照

| 验证过的结论 | 出处 | 我们的设计 | 判定 |
|---|---|---|---|
| **无外部反馈的"自我纠错"不可靠，甚至让表现变差** | [Huang et al. 2023, arXiv:2310.01798](https://arxiv.org/abs/2310.01798)（原文："LLMs struggle to self-correct their responses without external feedback, and at times, their performance even degrades"） | 审计是**独立角色 + 外部产物 + 机械阈值**，不是模型自查自己的推理 | ✅ **没踩坑**，这是当前设计最强的一点 |
| **把批判"接地"到外部工具（执行器/搜索/编译器）时收益最大** | [CRITIC, arXiv:2305.11738](https://arxiv.org/abs/2305.11738)（S2 实测 1058 次引用） | 阶段链 `toolsMounted=false`：审计与执行者都**没有**可调用工具；判据只能靠"读产物" | ❌ **明显出入**——我们停在"纯阅读式批判" |
| 迭代自反馈可提升输出，但收益依赖**可靠的评估信号** | [Self-Refine, arXiv:2303.17651](https://arxiv.org/abs/2303.17651)、[Reflexion, arXiv:2303.11366](https://arxiv.org/abs/2303.11366) | 我们的信号 = 契约+产物+题面事实+机械阈值，比"纯自我反思"强；但仍由 LLM 判定 | ⚠️ 中等：方向对，信号强度介于"自我反思"与"编译器"之间 |
| **LLM 评委存在位置/冗长/自我增强偏差**；同族评委偏向自己的输出 | [Judging LLM-as-a-Judge, arXiv:2306.05685](https://arxiv.org/abs/2306.05685) | 默认 `PAPER_AUDIT_MODEL = 执行者同模型`（可配置换族） | ⚠️ **默认配置踩在已知偏差上**（本次跑就是同模型） |
| **过程监督 > 结果监督**（逐步反馈优于只看最终结果） | [Let's Verify Step by Step, arXiv:2305.20050](https://arxiv.org/abs/2305.20050) | 只有阶段末一次结果级判定；长阶段（如 code 的 9 个分片）内部无步骤级监督 | ⚠️ 明显出入：粒度太粗 |
| 行业主流形态：**确定性 rails 优先 + LLM judge 兜底 + 修复回路** | [Guardrails AI](https://github.com/guardrails-ai/guardrails)（7.6k★，2026-10-27 活跃）、[LLM Guard](https://github.com/protectai/llm-guard)（3.2k★） | 机械门禁（确定性）+ 审计（LLM）+ 回灌（修复回路）三层**齐全**，顺序也对 | ✅ 架构形态与行业一致 |

### 3.1 归纳：四处"明显出入"

1. **同模型审计**（默认）：已知自我增强偏差；可一行配置换族，但当前默认值就是风险配置。
2. **阶段内无工具回路**：CRITIC 的核心结论是"批判要能调用工具"，我们连执行者都没有工具，
   审计也只能"读"，不能"跑"（例如无法自己重算一个数）。
3. **non-blocking findings 无归宿**：见 §2.3，违反项目自己的铁律。
4. **只有 outcome 级、无 step 级**：11 个模型阶段里，code 阶段 9 个分片、动辄 40 分钟，
   中间没有过程监督；错误只能在阶段末一次性暴露（本次实测：6 轮才收敛）。

## 4. 结论：这一角色是否有必要？

**有必要保留，但它的定位需要纠正。**

- **保留的理由（实证）**：本次三条 fatal（概率方向写反、零数字自白、产物缺失）全部是
  "结构合法、语义错误"，机械门禁 100% 抓不到；历史 2024B 的 `ce=40` 死参数也只有它能抓。
  去掉 L3 = 把这类错误的发现推迟到阶段 8 复核，代价是整段回滚（设计文档 §"为什么必须有它"
  的原始论证仍然成立）。
- **定位纠正**：它现在是"**阶段末判官**"，不是"阶段内提醒者"。用户想要的"工作中提醒"
  在当前实现里由 **L1 静态清单 + L2 回灌**承担，而这两者的共同弱点是**没有执行反馈**——
  模型被告知"不要犯 X 错"，但没有任何机制在它写错的那一刻告诉它。
- **不建议**新增一个"实时旁观的 LLM 审计员"：成本 ×11 阶段、延迟、且无验证过的收益
  （Huang 2023 的结论正是"无外部信号的 LLM 监督不可靠"；LLM-as-judge 的自我增强偏差
  在同模型下会被放大）。

## 5. 建议的形态（待裁决，**未实施**）

按成本从低到高：

| 优先级 | 动作 | 依据 | 成本 |
|---|---|---|---|
| **P0** | 审计模型默认改**不同模型族**（`PAPER_AUDIT_MODEL` 已支持，只需改默认策略/文档） | LLM-as-judge 自我增强偏差 | 一行配置 |
| **P0** | non-blocking findings **进交付已知缺陷表**（补一条消费路径） | 项目铁律"检出必须有归宿"；§2.3 实测缺口 | 小（一个消费点 + 测试） |
| **P1** | 阶段链挂载 `check_container`（`toolsMounted` 打开），让"提醒"变成"可执行自检" | CRITIC：工具接地收益最大 | 中（工具回路 + 提示词 + 测试） |
| **P2** | 分片级过程监督（每片交付后跑确定性检查，而非整阶段末） | Let's Verify Step by Step | 中高 |
| **不做** | 新增实时旁观 LLM 审计员 | 无验证收益 + 偏差放大 | — |

## 6. 需要裁决的点（S1）

1. 是否采纳 **P0 两项**（审计换模型族默认 + findings 进已知缺陷表）？
2. 是否采纳 **P1**（阶段链挂载检查工具）？——这会把"提醒"从静态文本变成可执行自检，
   但也改变阶段内交互形态（模型多一轮工具调用）。
3. **P2**（分片级过程监督）是否登记为后续任务？
4. 当前 L3 的阈值 0.7 是否维持？（本次实测：0.60/0.85/0.80/0.30 分档清晰，暂无调整依据）
