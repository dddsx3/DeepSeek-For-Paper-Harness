# 第五轮：把"可执行检查"接上主线（2024B / strict）

> **本轮做的事**：按"修复已暴露 → 清理未暴露 → 原子验证 → 全链路验证"的顺序走。
> **配置**：2024B × `deepseek/deepseek-v4-pro` × `strict` × 档位 A × `fail-soft`（与 strict-7 逐字同配置，
> 唯一变量是自检工具）。
> **日期**：2026-09-23

---

## 0. 结论先行

1. **工具通道在真实运行上打通了，模型确实会用它。** strict-9 的审计里有
   `E2SelfCheck calls=3` ×2 与 `calls=1` ×1——**用满额度**，不是礼貌性试一次。
   这一条回答了第四轮留下的问题（"模型会不会去用工具"）：**会**。

2. **容器级的机械失败被清零了，但交付档位仍然没有突破。**
   strict-11 的审计里 **`container_refused` 事件数为 0**——每一次提交的容器都通过了
   准入（strict-9 是 5 次容器级拒绝）。拒绝全部移到了**准入之后的产出链**上
   （参考文献相关性 ×4、图注数字纪律 ×1）。**`paper.docx` 第一次交付成功**
   （62,750 字节），`minted_ir_count` 138（strict-9 是 77）。
   但档位仍是 `DEGRADED`、路径仍是 `B-e1-direct`——**第五轮连续如此**。

3. **本轮抓到并修掉两个只在工具通道打开后才会出现的协议缺陷**，两个都是
   **静默**形态（症状不指向工具）：`content: null` 崩掉整次调用、工具调用回合
   被误判成空流。加上接缝丢 `tools` 那一处，共三处。

4. **本轮最重要的发现是一个缺口，不是一条修复**：模型用满 3 次工具额度，
   **然后照样提交了工具已经指出问题的容器**；而审计里只记了 `calls: 3`，
   **看不出工具当时报了什么**——于是"工具报了但它没改"与"工具根本没报"
   事后无法区分。已修（§4）。

## 1. 接自检工具的完整链路

| 层 | 文件 | 它负责什么 |
|---|---|---|
| 判据 | `src/produce/self-check.ts` | `checkCandidateContainer`：复用**真实准入路径**的判据 |
| 回路 | `src/executor.ts#callWithSelfCheck` | 工具定义、对话累积、轮次上限、结论回传 |
| wire | `apps/paper-shell/src/real-provider.ts` | harness 形状 → OpenAI 形状；SSE 里的 `tool_calls` 解析 |
| 接缝 | `apps/paper-shell/src/cli.ts` | 把 `tools` 与 `tool-result` 送过 shell 的 adapter |
| 指纹 | `apps/paper-shell/src/cassette.ts` | 带工具与不带工具是**不同的请求** |

**工具只有 1 个，且只读**：`check_container`。它不改状态、不碰文件、不执行代码，
所以即使被滥用，代价上限只是多几轮。

**它查什么**（都是"提交时可判"的）：

| # | 判据 | 对应准入拒绝 |
|---|---|---|
| ① | 容器可解析、版本标记是首键 | `parse_failed` |
| ② | `entries` 非空、每项 `{kind, value}` | `container 'entries' must be a non-empty array` |
| ③ | 容器内 id 不重复 | `conflicting_id` |
| ④ | 每个子问题都有自己的 ModelSpec | 逐问覆盖（A7 fail-closed） |
| ⑤ | Result 的 locator 在 `run.outputBasenames` 里 | locator 不解析 |
| ⑥ | **跨子问题引用合法（REF-003）** | `reference_scope_mismatch` ← **全轮次最高频** |
| ⑦ | **B3/B4/B5 保真**（复用 `checkE1E2Fidelity`） | `E1_E2_FIDELITY_VIOLATION` ← **第二高频** |

⑥⑦ 是本轮补上的。此前工具不查它们，于是模型要到**准入时**才发现——那时已经
烧掉一次完整的 E2 调用（strict-9 的 E2 单次输出 41KB、耗时数分钟）。

**它明说自己查不了什么**（`notChecked`）：`numeric_config.json` 的键、
每个 `jsonPath` 是否解析到有限数、章节篇幅。缺了这一项，"检查过了"会被读成
"全对"——那比没有工具更糟。

## 2. 三个只在工具通道打开后才出现的缺陷

### 2.1 接缝把 `tools` 吞了（静默）

executor 早就会发出 `tools: [check_container]`，`real-provider.ts` 也早就把它
转成 wire 形状。但**中间的接缝**（`cli.ts` 的 `adapterStream`）的类型是

```
adapter: (r, req: { system?: string; messages: Array<{content: string}> }) => …
```

——一个**装不下 `tools` 的类型**。它把请求重建成 `{system, messages}` 再转交，
工具定义就此消失；同样的原因，`tool-result` 内容块也被拍平成空串。

后果全是**静默**的：请求照样 200，模型只是永远没有工具可调。于是"模型不爱用工具"
与"工具根本没送到"在事后**无法分辨**。

这与本项目反复抓到的那类缺陷同源：**判定侧写了，传递侧没写**。修法除了补齐三处，
还加了一条**结构性不变量测试** `apps/paper-shell/tests/seam-forwards-tools.spec.ts`。

### 2.2 `content: null` 崩掉整次调用

**落盘证据**（strict-8，attempt 3）：
`provider_retry UNKNOWN: Cannot read properties of null (reading 'length')`。

根因：判据写的是 `delta !== undefined`，而 OpenAI 兼容端点在**工具调用分片**上
把 `content` 显式写成 `null`——`null !== undefined` 为真，随后 `delta.length` 抛异常。
没有工具时端点从不发 `content: null`，所以这是工具通道带出来的新形态。

### 2.3 工具调用回合被误判成空流

工具调用回合**本来就没有正文**。若端点没发 `finish_reason`（协议允许它只出现在
`[DONE]` 之前那一片），`classifyStream` 会判 `EMPTY_STREAM`——一次成功的工具调用
被判成失败。修法：`classifyStream` 增加 `sawToolCalls`；见到调用分片时零正文是正常的。
反向守卫仍在（没有工具调用时零正文 + 无 finish 依旧是 `EMPTY_STREAM`）。

### 3.1 strict-11 是分水岭：容器级失败清零

strict-11 的 8 次拒绝里，**没有一次是容器级拒绝**（审计里 `container_refused` 事件数为 **0**）。
每一次提交的容器都**通过了准入**；拒绝全部发生在**准入之后的产出链**上：

| # | 类别 | 次数 | 发生在哪 |
|---|---|---|---|
| 1 | `prose_contract`：参考文献与本文所用方法没有可辨的关联 | 4 | **产出链**（正文质量） |
| 2 | `figure_declaration_invalid`：图注里带了一个不指向 Result 的数字 | 1 | **产出链**（图注纪律） |
| 3 | B3 `e1_span 疑似改写`（相似度 27.9%） | 1 | 保真门——模型**在自检之后又改了** |
| 4 | `terminated` / `EMPTY_STREAM` | 2 | 环境（中转） |

**这一轮的两个"第一次"**：

- **`paper.docx` 交付了**（62,750 字节）。此前每一轮 docx 都被导出前校核拒掉
  （"表格列数不一" + "未填充占位"）。这一轮两项都过了。
- **`minted_ir_count = 138`**（strict-9 是 77，strict-8 是 65）：链在产出链里走得深得多。

**自检工具的收敛行为**（17 次调用，9 次判"可准入"）：模型是在**用工具迭代**。
最干净的一次是 attempt 3——**第一次调用就判可准入**（23,582 字）。

**所以瓶颈换了地方。** 不再是"容器写不对"，而是**"论文的正文质量不达标"**：
参考文献要指向实际用过的方法、图注不许出现游离数字。这两条都是**内容**判据，
不是结构判据。

### 3.2 strict-13：容器级失败仍是 0，而**一条**规则卡住了整条链

批准即收口上线后的 strict-13：**`container_refused` 事件数仍为 0**，工具 10 次调用里
**5 次判"可准入"**（收口生效：一次尝试只用了 2 轮就拿到干净容器并停止，而 strict-12
同样情形下会继续改到第 6 轮）。`minted_ir_count = 174`——**本架构跑过的最高值**。

而 7 次拒绝里 **4 次是同一条规则**：

```
figure 'FIG-Q2' caption/axis label contains numeric literal '2'
  that is not a referenced Result value [72, 72, 72, 72, 72, 72]
```

**游离的字面量每次都是 `2`。** 模型写的是"问题2 / 情形2 / 图2"。

**这一条值得单独说，因为它不是模型的缺陷，是措辞的缺陷。** 规则早就在宪法里
（`caption/x_label/y_label must NOT contain numeric literals`），但那条措辞对**中文
写作者**不起作用——没有人会把"问题2"里的 `2` 读成"数字字面量"。

修法是**改措辞，不是改判据**：在宪法里把陷阱点名（`CHINESE ORDINALS ARE THE TRAP`：
问题2 / 情形2 / 图2 / 第2问 各含一个字面量 `2`，各自被拒），并给出**合法改写**
（用中文数字"问题二"，或更好——直接命名而不是编号："抽样检验方案 / 生产决策"）。

方向性守卫（写进测试）：原禁令必须逐字保留。**这一轮加的是措辞，不是放松检查。**

这正是 W8.11-A1 已经教过一次的教训：**只加禁令不加理由，模型会换一种方式违反。**

**这 6 类里有 5 类落在自检工具能查的范围内。** 那为什么没拦住？

## 4. 本轮最重要的发现：工具报过，模型没改（且会停止使用工具）

strict-9 的审计（当时只有 `calls: 3`，看不出结论）：

```
21:32:50.099  E2SelfCheck  calls=3
21:32:50.141  provider_retry  E1_E2_FIDELITY_VIOLATION  attempt 4
              B3 正向: A-INDEPENDENT-PARTS: e1_span 过短（3 < 10）；…
```

**相隔 42 毫秒。** 工具跑完了（满 3 次），紧接着提交的容器里那些问题**一个都没改**。

这不是"工具没送到"，也不是"工具查不出来"，而是：**额度用完之后，工具说过的话
就随这一轮一起丢掉了**。模型把工具当成"提交前跑一遍看看"，跑到第 3 次发现还有
问题、没有额度了，于是**照样提交**。

两处修法（都不把工具变成门）：

1. **结论可取证**：`E2SelfCheckCall` 的审计现在带 `admissible`、`problem_count`
   与前 3 条 `problems`。此后"工具报了但它没改"与"工具根本没报"分得出来。
   ——**观测点必须在崩溃/丢弃点之前**，这是 strict-8 已经教过一次的事（那次连
   "工具是否被调用过"都无从判断），strict-9 又以另一种形式教了一遍。

2. **结论带过这一轮**：这一轮结束时若工具的**最后一次**结论是"不可准入"，
   那些问题会被追加进 `#e2ViolationsByRun`（code `SELF_CHECK_REPORTED`），
   于是**下一次尝试**的回灌里会写着"你自己调用的自检工具在提交前已经报出这些问题，
   但容器里它们仍在"。

   **这不是门**：准入判定一个字都没变，变的只是下一次尝试收到的提示文本。
   工具仍然只影响"模型看到什么"，不决定"容器能不能进"。

   实现上有一处必须留意的细节：回灌文本会被 `e2DriftGuidance` 逐行
   `stripNumericLiterals`（E2 的零数字纪律，每个数字换成 `#`）。**直接引用工具原文
   是错的**——`e1_span 过短（3 < 10）` 会被剥成 `e1_span 过短（ < ）`，读起来像乱码；
   `E1` 也会变成 `E#`。所以注入的那句话**按构造无数字**：只说问题类别，原文让模型
   自己再调一次工具去看。

### 4.1 strict-10 又教了一件事：模型会**停止**使用工具

strict-10 里工具只被调用 **1 次**（attempt 2），此后 attempts 3–7 **一次都没调**。

那一次的结论是：

```
E2SelfCheckCall  container_chars=41841  admissible=false  problem_count=1
                 problems=["容器无法解析：model output is not JSON: SyntaxError:
                            Expected ',' or '}' after property value at position 9195"]
```

工具告诉它"你的 JSON 在 9195 处坏了"，然后模型**再也没用过这个工具**，
接下来四次尝试全部以 `parse_failed` 收场。

这个行为有两种解释，而**它们指向不同的下一步**：
- 模型把"工具报了一次错"理解成"这个工具没用"；
- 或者 41KB 的容器本身就超出了它一次能可靠输出的规模，工具再准也救不回来。

**第二种更可能**：同一份容器它连写四次都没写完整，这不是"不知道规则"。

### 4.1b strict-12：把额度提到 6 之后，模型**不收敛，而是震荡**

strict-11 里"3 轮刚好走到干净、不够再确认一次"看起来像是额度不足。于是额度提到 6。
**结果是负收益**——strict-12 的 attempt 1 逐轮记录：

| 轮 | 容器字节 | 工具结论 |
|---|---|---|
| 0 | 19,730 | 不可准入 |
| 1 | 29,559 | 不可准入 |
| 2 | 40,017 | 不可准入 |
| 3 | 21,567 | **可准入** ← 已经拿到干净容器 |
| 4 | 38,835 | 不可准入 ← 又改坏了 |
| 5 | 23,271 | 不可准入 |

然后它提交了一份**连 JSON 都不合法**的文本。

strict-12 整轮的结果也一致：7 次拒绝里 **5 次是 `parse_failed`**（JSON 写不完整），
`minted_ir_count` 只有 10（strict-11 是 138）——链很早就掉到兜底路径。
（docx 仍然交付了，58,929 字节。）

**这一条纠正了本报告初稿的一个判断**：瓶颈不是"额度不够"，而是**缺一个终止条件**。
工具说"可准入"就是目标状态；而原来的循环**没有把它当作终点**，于是模型继续编辑、
把已经干净的容器改坏。额度越大，改坏的机会越多。

**修法（本轮最后一块）：批准即收口。** 工具一旦判"可准入"，harness 立刻要求模型
把那份文本**原样**作为最终答案给出，然后取走——不再执行任何工具，也不给它继续
编辑的机会。

**这不是把工具变成门**：准入判定一个字都没变。它只是把"工具说可以了"当作
**循环的终止条件**——一个自然的目标状态，而不是新的约束。

### 4.2 本轮补上的最后一块：闭 schema 检查

strict-10 的 attempt 2 被 `entry 'EquationSpec' violates its closed IR schema —
Unrecognized key: "token"` 拒掉，而**工具当时只报了"JSON 解析失败"**——闭 schema
违规它能查却没查。它是最机械可判的一类（字段名对不对），已补上（复用 `IR_SCHEMAS`，
与 store 的 `put` 同一张表）。

有意思的是：**我给工具写测试用例时，自己手写的 `EquationSpec` fixture 也被它判成
不合规**（缺 `expression`、`representation` 取值不对）。这条判据的有效性因此不是
推演出来的，是撞出来的。

## 5. 判据边界

- 每轮 **n=1**，五轮不能谈分布，只能谈"某类失败消失了没有"。
- **token 成本翻了近 3 倍**（583K/349K vs 204K/94K）：工具回路每一轮都带着完整
  对话重发。这是**已知代价**，不是缺陷；但若工具最终无法改善交付，这个代价就不值。
- `docx` 的拒绝是**诚实的下游判定**（表格列数不一致），不是导出链的缺陷。
- `costUsd` 恒 0（路由未配价格表）；token 是实测的，金额不是。
- 我**没有**评估论文的建模正确性——本报告只回答"机制是否生效、瓶颈在哪"。
- **strict-8 的工具调用情况不可知**：那次 `content: null` 崩在审计写入之前。
  这条缺口已修（逐次调用在跑判据之后立即记痕），但 strict-8 的历史数据无法补。

## 6. 现在的真实瓶颈

五轮下来，交付档位没动过。把拒绝按"谁该负责"归类，结论很清楚：

| 归属 | strict-9 | strict-10 | **strict-11** |
|---|---|---|---|
| 容器级（准入拒绝） | 5 | 6 | **0** |
| 产出链（准入之后的内容质量） | 1 | 0 | **5** |
| 环境（中转） | 1 | 1 | 2 |
| harness 机制 | **0** | **0** | **0** |

**容器级的机械失败已经被工具清掉了。** 这不是"模型变仔细了"，而是**判据前移**了：
模型在提交前自己跑一遍检查，改到工具说"可准入"为止。三次真实运行（strict-9 → 11）
正好是这条判据从"没有"到"有"的过程。

**瓶颈换成了内容质量**，而这一条**不该由容器级工具承担**：参考文献是否指向实际
用过的方法、图注里的数字是否指向某个 Result——这些**在容器里看不出来**，要看
渲染后的正文与图。它们属于 L5 评审与产出链自己的判据。

**为什么产出链的拒绝仍然导致 E2 重试**：产出链在 EXECUTE 节点内运行，它拒绝时
整个节点重试，于是**再花一次完整的 E2 调用**（40KB 输出、数分钟）。这是当前最大的
成本浪费——strict-11 用了 **836K/454K tokens**（strict-7 的 3 倍）。

**下一步的方向因此变了**：不再是"让模型更仔细地写容器"，而是
**（a）让产出链的拒绝能局部返修而不是整节点重试**，
**（b）把内容质量判据（参考文献相关性、图注数字纪律）做进那一步的简报**。

## 7. 下一步（按信息量排序）

| # | 动作 | 判据 |
|---|---|---|
| 1 | **产出链的拒绝不再整节点重试**（局部返修） | token 成本是否回落；同一处拒绝是否被反复触发 |
| 2 | ~~内容质量判据进简报~~ → **已完成**：宪法点名中文序数陷阱（strict-13 的头号阻断） | `figure_declaration_invalid` 是否下降 |
| 3 | ~~工具额度 3 → 6~~ | ❌ **已测且为负收益**：额度越大越震荡。改为"批准即收口" |
| 4 | 到顶那一轮**不给自由文本**（只接受 JSON 或工具调用） | 消除 `"I need to "` 这类放弃式输出 |
| 5 | E2 拆成逐问多次调用 | 单次输出字节数下降（若 `parse_failed` 复发则优先） |

**为什么第 1 条排在第一位**：strict-11 的 8 次拒绝里有 5 次是产出链的，而**每一次
都重跑了一遍 E2**（40KB 输出、数分钟、近百万 token）。产出链的返修对象是正文与
图注，**根本不需要重新声明整个容器**。这是当前最大的一处成本浪费，也是唯一一处
"重试的东西与失败的东西不是同一个"的地方。
