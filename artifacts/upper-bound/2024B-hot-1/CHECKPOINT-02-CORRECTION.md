# 检查点 02 修正 — 我的判据方法有误

> 修正对象：`CHECKPOINT-02-declare.md` §3 与 §7 的结论
> 发现时机：写检查点 03 时（对比合并前后的判据）
> 日期：2026-09-24

---

## 1. 错在哪

检查点 02 我写了：

> **这份容器若直接进产出链，`prose_contract` 必然拒绝**……`analysis` 72 字 / 1200、
> `evaluation` 49 / 800、`references` 124 / 600、`code` 96 / 600、`restatement` 32 / 200

**这个检查方法错了。** 我检查的是**容器的原始 `narrative`**，而产出链检查的是
**合并之后的 narrative**。

`runProductionChain`（`executor.ts:2294` 起）在跑契约之前会做三处注入：

| 注入 | 源 | 目标章 |
|---|---|---|
| E1 的逐问段（`[[REQUIREMENT: R-Qn]]`） | `perQuestionSectionsOf(e1FullText, …)` | `analysis` |
| E1 的统一框架段 | `frameworkOf(e1FullText)` | `methods` |
| **容器的真实代码** | `container.code` | `code` |

所以 `analysis` / `methods` / `code` 三章**不是模型单独写的**，它们带着 E1 的 7,173 字
与 3,949 字的代码。用原始 narrative 判它们，等于**凭空多报了三条违规**。

## 2. 正确的检查（`scripts/.check-merged.mts`）

按产出链的合并规则重建 narrative 之后再跑契约。对**第一轮**（`02-declare`）的正确结论是：

| 章 | 合并后字数 | 地板 | 判定 |
|---|---|---|---|
| `analysis` | 3,000+（E1 逐问段注入） | 1200 | ✅ PASS |
| `code` | 3,000+（真实代码块注入） | 600 | ✅ PASS |
| `restatement` | — | 200 | ✅ PASS |
| **`evaluation`** | **49** | 800 | ❌ FAIL |
| **`references`** | **124** | 600 | ❌ FAIL |

**结论仍然成立**（第一轮确实会被拒），但**理由完全不同**：不是"八章大面积不达"，
而是**恰好两章不达——而且正是 E1 不注入的那两章**。这个区别是决定性的：
它把"模型写得不好"改写成了"这两章没人帮它兜底，而它不知道"。

## 3. 教训（写给下一个核查者）

**检查点用的判据必须与门禁用的判据是同一个东西。** 我在 round-6 的
`prose_contract` 复验器上刚修过同一个错误（读 `narrative` vs 读渲染文本，
两者在兜底路径上会分叉），这一轮自己在**核查脚本**里又犯了一次。

两次都是同一个形状：**我拿了一个"看起来等价"的输入去跑同一个函数**。
函数没变、判据没变，变的是输入——而输入不等价时，结论就是错的，且**看不出来**。

所以核查脚本 `.check-merged.mts` 的注释里写明了它复现的是哪几行合并逻辑，
以及为什么必须复现：**目的是让"检查点看到的"与"产出链判的"是同一个东西。**

## 4. 附带发现：核查脚本比 harness 更严格（同样是输入不等价）

第一轮核查时容器被模型包在 ```` ```json ```` 围栏里，我的脚本直接 `JSON.parse` 就炸了，
而 harness **按设计会剥一层围栏**（"the fence is a RENDERING difference — the JSON
inside is the same object"）。

也就是说我的核查脚本当时报的"不可解析"是一个**假红**——它比门禁更严格。
已修：脚本按同款规则剥围栏，并在注释里写明为什么。

**这是同一类错误的第二个实例**：核查侧与门禁侧对**同一个输入的容忍度不同**，
于是核查报的问题门禁根本不认。两条都记在这里，供后续核查脚本的作者避坑。
