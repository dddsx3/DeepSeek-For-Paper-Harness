## 1. 数字指控：成立，且更严重

审计复算 strict-11 摘要的两个数字，结论成立。我独立复算，**逐位一致**：

| 论文声明 | 约束 | 真值 | 判定 |
|---|---|---|---|
| 情形(2) n=46, c₂=2 | P(X≤2 \| 46, 0.1) ≥ 0.90 | **0.1484** | 🔴 差 6 倍 |
| 情形(1) n=29, c₁=6 | P(X≥6 \| 29, 0.1) ≤ 0.05 | **0.0637** | 🔴 仍越限 |

**而且更糟——论文的"结果"章是一句伪造的验证结论**：

> 问题1的样本量与临界值通过精确二项分布验证：情形(1)在 \(n=29, c_1=6\) 时第一类错误为 **0.0473**，满足不超过 5% 的要求

真值 0.0637；**0.0473 对应的是 (27,6)**。也就是说：一个自称"通过精确二项分布验证"的数字，
本身是错的。这比"未验证的数字"更危险——它主动宣称了可信度。

（对照：strict-13 同章写的是 `{R-N1}`/`{R-C1}` 占位符。诚实，但空。两种形态都在，
恰好构成审计所说"分裂态"的两极。）

## 2. 全链排查：查出两处审计未报的洞

审计把 `reference_validation` 列为产出链的拒绝码之一。**它不在产出链里**——它是交付层
门（`src/delivery/gate-registry.ts:304`），跑在所有节点之后，且从不回到尝试循环。
strict-11 那条参考文献拒绝的真实来源是 `prose_contract` 的第 3 条规则（参考文献 ≥3 条
且至少一条含方法关键词）。这个区别重要：交付层门拒绝时**没有任何重试**。

### 洞一（上游）：兜底稿的"如实说明"被修订轮整章改写

兜底稿（`e1-direct.ts`）对产不出的章写的是**如实说明**：

> 本稿没有模型评价与推广：这一章由结构化规范化（E2）产出的容器提供，本次规范化未通过……

而交付出去的 strict-11 里，那一章是 **1,193 字的真内容**，参考文献章是 **425 字的条目表**。
它们不是兜底稿写的，是**修订轮**（review→revise）写的。修订轮：

- 输入输出都是**自由文本**
- 唯一守卫是 `revisionDestroysDraft`（标题集合 + 长度 ≥50%）
- **从不经过 `proseContractViolations`**（那条判据读 `narrative`，兜底路径根本没有 narrative）

所以那两章是**一次从未被任何契约检查过的自由文本改写**——而"0.0473"就是这次改写写出来的。

### 洞二（下游）：`prose_contract` 的复验在兜底路径上静默空转

`RECHECKERS['prose_contract']` 读 `input.narrative`。兜底路径的 narrative 是空的，
于是复验检查的是一个空对象——它永远"通过"，而它本该校验的东西根本没被看。

### 修法（已实现）

1. **`proseContractViolationsOfText(markdown, requirements)`**：把渲染后的正文按 `## ` 章
   切开、映射成契约读得懂的伪 narrative，**复用同一套规则函数**（`proseContractViolations`
   + `substanceViolations`），两条路径的判据因此不可能漂移。
2. **在交付前对最终正文重跑它**，违规逐条进 `gradeInput` → 落进交付附录的已知缺陷表。
   **不拒绝任何东西**（兜底的意义是"总得交出点东西"），只让违规可见。
3. **`numericClaimCensus(markdown)`**：正文里（排除代码块与 `{<result_id>}` 占位符）
   数字字面量的个数。兜底路径下生成一条 `unverified_numbers` finding（major），
   写明"这 N 处数字全部未经代码通道验证，稿中若有'经…验证'的句子那是模型自述"。
4. **复验器登记 `unverified_numbers`**：判据是"降到 0 才算修好"——用"数量下降"当判据
   会让"改掉一个错数字、又写下另一个"混过去。
5. **`prose_contract` 复验器**改为按 `narrative` 是否为空选择输入，与报告该 finding 的
   那一次**同源**（否则复验检查的不是同一个东西——那是另一种假复验）。

### 标注完整性：四条导出路径逐一核查

审计担心 DEGRADED 横幅可被剥离。核查结果：**目前四条路径全部保留**（对真实产物验证，
非读代码推断）：

| 路径 | 结论 | 依据 |
|---|---|---|
| `report.md` | ✅ | 唯一的一份 markdown，所有导出都读它 |
| `paper.pdf` | ✅ | `export-pdf.py` 无 `【` / `## 附录` 过滤；pypdf 抽取实测含"交付状态""未逐条溯源" |
| `paper.docx` | ✅ | `export-docx.py` 把横幅当普通正文段落；`>` 分支只剥 `>` |
| `deliverable.zip` | ✅ | 包内 `report.md` 是同一个变量 |

**缺口已补**（`apps/paper-shell/src/deliverable-guard.ts`）：交付前跑一次防伪守卫——
档位非 CLEAN 时，稿子里必须能找到档位抬头；`B-e1-direct` 还必须能找到
"未经规范 IR 验证"那句说明。**找不到就拒绝交付**（`DELIVERY REFUSED`，退出码 1），
而不是导出一份没有标记的成品。

守卫的判据是"**标记在不在**"，不是"导出路径对不对"——所以它对未来新增的导出路径
同样生效（有一条用例专门钉这一点）。8 条测试。

（仍然保留的局限：它检查的是**交付前的那一份 markdown**，无法阻止有人在交付**之后**
手工编辑产物。那是流程问题，不是代码能守的。）

## 3. P2 已实现：到顶轮只收结构化输出

`callWithSelfCheck` 此前在到顶那一轮**无条件收下**模型给的一切文本。实测后果：

```
parse_failed: Unexpected token 'I', "I need to "... is not valid JSON
```

一句放弃声明被当成提交，整次尝试判 `parse_failed` 并**重跑一整个节点**——一次完整的
E2 调用就为了一句"我做不到"。

修法：
- 新增判据 `isStructuredAnswer(text)`（宽松到"含不含 JSON 对象"——精确 schema 判定仍归
  `parseModelContainer`；在这里严格判定会让"JSON 但 schema 差一点"被误当散文重问，
  而它本该走正常的 DRIFT 回灌）。
- 到顶/批准后若交回散文：**不收**，明确回一句 `STRUCTURED_ONLY_CORRECTION`，再取一次
  （只再要一次：第二次仍不给，说明它这轮确实产不出，如实交回）。
- 交回时带 `notStructured` 标记，调用方给出**精确的拒绝理由**
  （`E2_PROSE_NOT_CONTAINER`：模型放弃了结构化输出），而不是下游那条 JSON 语法错误——
  旧报错指向症状，回灌也就治不对地方。

测试 3 条（含反向守卫：正常交容器时不多问）。

## 4. P0 为什么没做：审计的落点有误

审计的 P0 是"产出链拒绝改为局部返修（不重跑 EXECUTE 节点）"。方向对，但**在节点层做
会撞上两个实现约束**，我核到了：

1. **运行命名空间是按尝试编号的**：`scopeAttemptId(id, attempt) = attempt <= 1 ? id : `${id}-a${attempt}``
   （`executor.ts:294`）。产出链在拒绝之前**已经铸了 RunArtifact 与 Result**，所以
   "拿同一个容器再跑一次链"会撞 `duplicate_id`。要么给修复轮一个新的尝试号（于是
   `displayIdOf` 的剥离必须同步改，否则 `-a1001` 会漏进交付的论文），要么换落点。
2. **节点层重入会连代码一起重跑**：`runProductionChain` 每次都调 `produceRunExecution`。
   审计说的"重跑一次 40KB 的 E2"确实省掉了，但沙箱执行又被重复了一遍。

**更小也更安全的落点**：把修复轮放进 `runProductionChain` **内部**——在代码跑完、
产物铸完之后，只对"narrative → 渲染 → 契约检查"这一段做修复循环。这样
不新增任何 id、不动命名空间、不重跑代码，而拒绝的对象（正文）与重试的对象
（正文）**终于是同一个**。代价是要把那个方法的长尾抽成可重入的一段，并给它传入
`role`（目前它拿不到，修复要发模型调用）。

这是本轮**未完成的第一优先项**。

## 6. 判据边界

- 本轮**没有真实运行**，全部结论来自代码核查 + 单元/集成测试 + 对已落盘产物的独立复算。
- 审计的 n=1 警告仍然成立：每轮一次运行，"某类失败消失了"可信，"不会回来"不可信。
- 我没有评估论文的建模正确性；§1 的复算只针对**论文自己声明的约束**。
- 数字普查会**多报**（`情形(1)` 里的 `1` 也算数字字面量，与图注判据同一口径）。
  这是有意的：这条 finding 的用途是"告诉读者这稿的数字没验证过"，少报才是危险的。
