## 候选 1：契约先行 + 每片只给"契约原文 + 本问规格"（专家 §三，我把它落成具体设计）

**设计**：
- 新增第 3.5 阶段（模型，一次小调用）产出 `contract.py`：`load_params()` 从框架写的
  `params.json` 读参数；零件/成品 dataclass；`write_result(qid, dict)`；每问必须暴露的
  函数签名（q2: `expected_profit(case, strategy)` / `best_strategy(case)`；
  q3: `evaluate_tree(tree, decisions)`；q4 import q2、q3，只换输入分布）。
- 阶段 3 的每片 prompt **不再内联全量简报**，只含：`contract.py` 原文 + 本问的
  模型规格（从建模阶段的 IR 声明切片）+ 本文件要实现的签名 + 一句"规格已定，逐行实现"。
- `main.py`、`DELIVERABLES.json` 由框架确定性生成（编排顺序与产出清单都是已知的），
  模型片从 6 减到 4（逐问 3 片 + contract 1 片）。

**机制**：诊断显示小 prompt 直接给答案、全量简报必然长推理——输入体量与推理长度强相关；
且"重新分析整道题"正是跨片不一致的来源。契约先定，后片只做填空。

**我的疑问（请判断）**：
- a) `contract.py` 由模型写还是框架模板生成？模型写能贴合题目语义，但多一次调用与一道门禁。
- b) 每片只给契约+本问规格后，**该问的求解难度仍在**（q3 的装配树递推、q1 的抽样搜索）——
  "规格已定，逐行实现"是否足以让模型跳过推理？还是难度本身就会逼出长推理？
  若是后者，是否应叠加候选 2（设计/转写分离）？

## 候选 2：设计片 / 转写片分离（专家"顺着它走"的思路，我落成两段式）

**设计**：每问两片。**设计片**允许（甚至要求）推理，产出 ≤40 行的算法规格：
输入/输出、算法步骤（伪代码）、要写的函数、结果键名。**转写片**拿着规格 +
`contract.py` 原文写代码，prompt 明说"算法已在规格中确定，逐行转写，不要重新设计"。

**机制**：推理是模型确有价值的部分，堵不如疏——把推理从"写代码时"挪到"写规格时"，
规格是短产物（~1k token），转写片的推理量应大幅下降。

**我的疑问**：转写片如果仍然写长推理（模型可能"顺手"验证规格），除了 prompt 约束外，
是否应直接上候选 4 的早停闸门（见下）作为硬兜底？两者叠加是否足够？

## 候选 3：前缀续写（prefill）与"伪前缀"探针

**设计**：两步探针脚本（复用上轮 `llm-relay-diagnose.mjs` 的骨架）：
- 3a：对中转发 `base_url + "/beta"` + 末条 assistant `{prefix: true, content: "```python\n"}`
  + `stop: ["```"]`，看是否 400/透传/生效；
- 3b：不依赖 `/beta`——messages 以 assistant 消息结尾（无 prefix 字段），看后端是否
  续写（部分 OpenAI 兼容后端支持）。

**机制**：官方文档明确支持（需 /beta），且示例场景与我们完全一致（"```python\n" 前缀
+ stop 截尾）。上轮已判"中转普遍不支持"，但我想要一个**5 分钟的实测判据**而不是推断。

**我的疑问**：若 3a/3b 都不通，"尾部锚点续写"（截断后取尾部 30 行作为 user 上下文，
"从中断处继续，不得重复已有行"）在实践中是否可靠？代码续写最常见的失败是重复
与接口漂移，有没有更稳的锚定方式？

## 候选 4：流式早停闸门（专家 §一.4，我落成具体判据）

**设计**：流式消费时维护两个计数器，超限即主动断流并标记失败原因（不烧完 65k token）：
- **content 头部闸门**：前 300 字符若不匹配本片期望的形态（代码片：`import`/`#`/`"""`/
  ``` ``` ```；声明片：`{`；散文片：不设），立即断流，失败原因"content 以推理开头"，
  自动升级重试（叠加候选 2 的转写 prompt）；
- **推理/散文熔断**：单片 content 超过 `max_tokens` 的 60% 仍未出现交付物起始标记
  → 断流。

**我的疑问**：断流后**同一片**立即重试几次是合理的？还是应该把"闸门触发"视为
该片的确定性失败、直接走修复/升级路径（避免烧钱循环）？

## 候选 5：模型路由（按"content 推文比"探针选模型）

**我的疑问**：DeepSeek 系之外，中转上常见的低推理倾向模型（如非推理版 V3、其他家

## 候选 6：params.json（输入侧"数不由模型持有"）

**设计**：阶段 1 的 `PROBLEM_FACTS.json`（每数带原文锚点）→ 框架确定性转成

**我的疑问**：q1 的"95%/90% 置信水平"这类**决策参数**（题面给语境、方案由模型定）

## 候选 7：压缩判据补强（专家 §五，我落成清单）

在现有"数字多重集守恒 + 锚点逐字在 + 围栏成对"之上新增：
- 单位/否定/条件/量词词表守恒（"元/件"、"不检测"、"若拆解"、"至少"、"不超过"）；
- "数字+最近名词"配对抽检（压缩前后配对关系不变）；
- 表格行守恒升级为"行内单元格逐字守恒"。

**疑问**：词表守恒会不会把压缩率打到不可用（保护行占比过高的文档等于没压）？
是否应该改为"守恒 + 显式声明丢弃"两段式（丢弃项列进简报头部让模型知情）？

## 候选 8：跨片一致性的兜底——账本对账

无论分片怎么切，最终一致性由既有机制兜底：harness 真跑代码 → 按
`RESULT_SOURCES.json`（locator+json_path）从产物字节铸账本 → 图表/论文只引用账本。

**疑问**：这个兜底是否足够替代"跨片接口一致性"的事前保证？还是事前
（候选 1 的契约）+ 事后（账本对账）必须双保险？
