## 2 实验暴露并已修复的问题（全部有留档证据）

| # | 错误形态 | 根因 | 修复 |
|---|---|---|---|
| 1 | `The operation was aborted due to timeout`（阶段 1 在 ~5 分钟、阶段 3 在 ~15 分钟被杀） | **墙钟上限误杀慢但健康的生成**：高质量产出时长不可预测 | 无令牌看门狗 `PAPER_IDLE_TIMEOUT_MS`（每收到 chunk 重置，持续 240s 无字节才失败）；连接超时信号**不得**留在响应上（会连流式 body 一起掐断，实测 10s 处被杀） |
| 2 | `terminated`（十几分钟的流被中转掐断） | 阶段链 `callModel` 无重试，一次传输失败整阶段作废 | 传输级重试 3 次（5s/15s/45s）；`max-tokens` **不重试** |
| 3 | 回答 270KB、四个独立围栏块、**没有 JSON 信封** | 映射规则只写在 runner.ts 模块头——**模型看不见** | 简报 `answerFormOf` 显式教回答形态（与解析规则同源，测试钉住） |
| 4 | 信封解析失败（散文里的 `{` 被当起点；信封后拖尾巴） | 单一解析规则扛不住"先推理后产出" | 候选阶梯：整个回答 → 契约锚（最后一个 `"files"`）+ **括号配平** → 首尾大括号；全失败时逐级点名 |
| 5 | `EISDIR ... 03-code\code` | 模型把注册表的 `code/`（dir）当信封键回声 | runner 认出目录回声（前缀下有真文件则忽略，没有则点名）；简报教"目录不单独作键" |
| 6 | `results[0] 的 value 不是有限数`（34/38 是对象值） | 渲染器/IR 只画标量，简报没说 | 简报补"`value` 必须是单个有限数，结构化的量拆成多条" |
| 7 | 阶段 1 清单 `fig_x\|问题1…（折线图）` 18 条全部不识别 | 解析器按整行裸名匹配 | 条目身份取 `\|` 之前；题注不进对账键 |

### 5.2 阶段 3 仍被 max-tokens 截断 —— 根因已定位到中转天花板

拆分后阶段 3 只需交付代码文件（交付体量已大幅收窄），连续三次（含内联预算砍半）
仍在 max-tokens 处截断。结合 W8.9-D1 的探针记录（"reasoning_effort: none 后同一
prompt 在 **8000 tokens** 就产出 content"），判定：**该中转对单次输出有约 8k 令牌的
硬天花板，与请求的 max_tokens 无关**。2024B 的建模代码需要长推理，天花板内装不下。

**这不是契约能解决的**（已经收窄过两次），下一步的正确形态是仓库已有的成熟机制：
**分片（shard）**——与 `shard-declare`（把容器声明按子问题分片成多次调用）同一模式，
把阶段 3 的代码按"编排入口 + 逐问实现"分片成多次调用，每次只产出一个 problem\*.py。
这是明确的实施项，未在本轮擅自实现（涉及阶段 3 与执行环节的契约变更）。

### 5.3 经验沉淀（写给下一轮）

1. **每阶段停 + 人工放行**让所有失败都停在单阶段内，`_rejected-answer.txt` 与
   `_gate-report.json` 让每次失败都可定位——本轮 9+ 个问题全部由此定位。
2. "数由谁持有"是建模管线的第一性契约：模型持有数，一致性与可追溯都不成立。
3. 输出天花板是**环境常量**，不是请求参数：所有"一次调用交付 X"的设计都要按
   ~8k 令牌预算反推 X 的上限，超了就分片。


## 6 追加：非流式实验（用户建议，已试）——否定结论但有价值

PAPER_NON_STREAM=1（一次拿完整 JSON）实测：**provider http 524**——Cloudflare 网关
"源站超时"（非流式下中转要等完整生成再应答，网关 ~100s 掐断；重试 3 次全 524）。

结论：**长生成场景下流式是唯一可行形态**。非流式把"输出天花板"问题变成了更糟的
"网关超时"问题。已实现并保留该模式（带总时长上限与工具回落），但默认流式 +
无令牌看门狗是正确组合。**阶段 3 的最终解仍是分片**（按"编排入口 + 逐问实现"
拆成多次调用，复用 shard-declare 的既有模式）。


## 7 追加：分片调用已落地 —— 剩余根因变为"模型把推理写进正文"

阶段 3 分片（code-shard.ts）已实现并测试：问数 N → 入口 1 片 + 逐问 N 片 + 收尾信封 1 片，
每片 prompt = 完整简报 + "本次只产出 X"；组装后按原契约解析（runner 不感知分片）。
2024B 实测：分片生效（6 片逐片调用），但仍 max-tokens——**证据**：单次回答
`_rejected-answer.txt` 达 1,084,277 字节（≈6.5 万令牌，恰为我们请求的 max_tokens，
被中转如实执行）。内容以 "Let me und…" 开头：模型把**巨量推理写进正文**，
一个文件的交付也压不住。

**结论**：这不再是管线架构问题（13 阶段、铸数、分片、压缩、看门狗均已就位），
而是**模型行为 × 请求参数**问题。可选对策（按代价排序）：
① 换推理更收敛的模型跑阶段 3（能力画像 L0 已有探针机制）；
② 分片 prompt 前置硬禁令 + few-shot（只给文件骨架，不给思考空间）；
③ 若中转支持 `reasoning` 参数的强制关闭，验证其对该模型的实际效力
   （W8.9-D1 的 8000-token 结论来自探针，需在 2024B 全量 prompt 上复核）。
