# 专家咨询：LLM 长代码生成被输出上限截断的问题汇总

> 本文自包含：不需要任何项目背景即可理解。先说系统与现象，再列已排除的方向，最后是需要请教的具体问题。

## 一、系统是什么

一个"数学建模竞赛论文"自动生成管线（类似把 CUMCM/国赛做题流程自动化）：

1. 模型按流水线分阶段工作：赛题分析 → 建模 → **写求解代码** → 声明图表 → 渲染图表 → 评审 → 写论文（Markdown）→ 改进循环 → 导出 Word。
2. 共 13 个阶段，每个阶段一次或多次 LLM 调用；阶段间以磁盘上的产物文件 + 机器可校验门禁交接，每个阶段有独立通行证，支持"跑完一个阶段停一下、人工检查后放行下一个"。
3. **数值不由模型持有**：模型写好 Python 求解代码后，由框架真实执行代码，再按模型声明的"数在哪（文件+路径）"从执行产物里提取数值铸成账本——图表/论文引用的每个数都定位到一次真实执行。
4. 图表渲染、格式校验等是框架侧的确定性代码，不经过模型。

## 二、环境

- 模型：`deepseek-v4-pro`（第三方 OpenAI 兼容中转，Cloudflare 防护）。
- 调用形态：流式 SSE（OpenAI chat.completions 兼容）；已实现非流式模式用于对比。
- 任务规模（2024 年 B 题"生产过程决策问题"）：4 个子问题，需要产出编排入口 + 4 个逐问求解脚本 + 结果说明 + 交付清单，代码含抽样方案搜索、16 策略期望利润枚举、多工序装配树递推等。

## 三、核心问题

**阶段"写求解代码"的单次调用，稳定被输出上限截断；即使每次调用只要求一个小文件也一样。**

### 现象与证据

1. 请求参数：`max_tokens: 65536`。流式返回在约 **1,084,277 字节**（≈6.5 万 token）处被 `finish_reason: length` 截断——即请求的 max_tokens 被如实执行，但不够用。
2. 截断的回答以 **"Let me understand…"** 开头：模型把**大量思维链写进了 content 正文**（不是单独的 reasoning 通道），正文里推理先于代码，预算被推理吃掉。
3. 请求里已带 `reasoning_effort: "none"`（对齐 W8.9-D1 探针结论：该参数能让 content 在 ~8000 token 处出现），但在此全量任务 prompt 下模型仍在 content 里写长推理——**参数似乎对该模型/中转不生效，或效力有限**。
4. 已实现"分片"：把阶段拆成 6 次调用（编排入口 1 片 + 逐问脚本 4 片 + 结果说明/清单 1 片），每片 prompt = 完整上下文 + "本次只产出某个文件，从第一个字符到最后一个字符都是它，不得有任何解释"。**分片后单片仍截断**（同样 65k token 用尽）——推理散文单片也装不下。
5. 输入侧已做"结构保持压缩"（数字/约束句/表格行/代码块/锚点逐字保留，只删解释性散文，上游内联 24k 字符预算），输入不是瓶颈。

### 次生约束（已实测）

- **非流式不可用**：Cloudflare 网关在 ~100 秒处掐断源站（HTTP 524），长生成无法一次拿完整 JSON；重试 3 次全 524。→ 长生成只能流式。
- **流式下有"无令牌看门狗"**（持续无字节才断，默认 240s），长生成本身可以跑很久，不是问题。
- 传输层偶发 `terminated`/`ECONNRESET`/`fetch failed`，已有指数退避重试（3 次），可用。

## 四、已排除/已落地的方向（请勿重复建议）

| 方向 | 结果 |
|---|---|
| 把"写代码"从一次大调用拆成 13 个阶段、每阶段独立契约与门禁 | ✅ 已做，架构层面收益明确 |
| 按子问题分片（每片只产出一个 .py 文件） | ✅ 已做；单片仍因 content 内推理超预算 |
| 输入压缩（保护数字/约束/表格/代码，只删散文；数字多重集守恒的可机检查证） | ✅ 已做；输入不是瓶颈 |
| 提高 `max_tokens` 到 65536 | 已生效（截断点后移到 65k token），但仍不够——瓶颈是推理吃预算 |
| `reasoning_effort: "none"` | 已默认发送；全量任务 prompt 下似乎无效（见上） |
| 非流式 | ❌ Cloudflare 524，不可行 |
| 墙钟超时 | 已改为"无令牌看门狗"（只在持续无字节时断），长生成可完整跑完 |
| 传输重试（terminated/ECONNRESET/fetch failed，指数退避） | ✅ 已做 |
| 数值由框架从执行产物提取（模型不写数值） | ✅ 已做（同时也消除了数值一致性与可追溯性问题） |

## 五、想请教的问题

1. **content 内思维链的抑制**：对 DeepSeek 系（或经中转的 OpenAI 兼容端点），`reasoning_effort` 之外，是否有被验证有效的方法让模型**直接输出代码/文件内容、不写分析散文**？（例如 assistant prefill / 首帧前缀续写——中转是否普遍支持？`chatml` 的 `<|Assistant|>` 前缀对 DeepSeek 端点是否可用？）
2. **输出上限的真实边界**：DeepSeek 系模型经中转时，`max_tokens` 的实际可设上限与默认值是否有公开文档？我们观察到请求 65536 会被如实执行到 65k token 仍 `length` 截断——是否应理解为"该模型单次 completion 上限就是不够这类任务"，从而**必须**分片？
3. **长代码生成的成熟模式**：在输出 token 有硬上限的前提下，生成一份多文件、相互引用的代码工程，业界推荐的形态是什么？（逐文件分片 + 固定接口约定？骨架→逐函数续写？以 assistant 前缀续写保证跨调用一致性？）跨调用之间如何保证前后一致（后一片引用前一片定义的函数/变量）？
4. **推理预算控制**：DeepSeek 是否暴露"思考预算"类参数（如 `thinking.budget_tokens`）？经中转是否会透传？
5. **压缩策略评审**：我们的"结构保持压缩"（保护数字/约束/表格/代码/锚点，删解释性散文，可机检数字多重集守恒）是否有明显缺陷或更优的既有方案？

## 六、一句话版

> DeepSeek-v4-pro 经 OpenAI 兼容中转做长代码生成时，会把巨量思维链写进 content（单次回答 1MB、`finish_reason=length`），`reasoning_effort:"none"` 与 `max_tokens:65536` 均无法让它直接给出代码；非流式又被 Cloudflare 524 掐断。按文件分片后单片仍被推理占满预算。求：让该模型"跳过 content 内推理、直接产出代码"的可靠方法，或长代码生成在输出上限下的标准工程模式。
