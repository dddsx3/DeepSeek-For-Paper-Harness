## 1. 结论：根因消除，失败整体下移

| 运行 | 拒绝总数 | **REF-003（根因）** | E1→E2 保真门 | **生产链（下游）** | 传输（中转空流） | 容器结构 |
|---|---|---|---|---|---|---|
| strict-1（修复前） | 7 | **3** | 3 | 0 | 0 | 1 |
| fast-1（修复前） | 7 | **4** | 1 | 0 | 0 | 2 |
| **strict-2（修复后）** | 8 | **0** ✅ | 0 | **4** | 3 | 1 |

**读法**：

- **`REF-003` 从 7/14 降到 0/8。** 修复前它是首要失败原因；修复后**一次都没出现**。
- **失败整体下移到生产链**（0 → 4 次）。这正是"瓶颈被挪开"的信号：容器**被准入了**，
  生产链真的跑起来了，于是失败发生在**更靠后**的、正常的门禁上。
- **token 反而更省**：strict-1 用了 213,797 in / 92,393 out；strict-2 用了
  **175,219 / 88,612**——做同样的活（3 视角 × 4 轮评审全跑完），少烧了约 18%，
  因为不再有 7 次尝试撞在同一堵墙上。

## 2. 修的是什么

**契约缺口**：每条 `AssumptionSpec` / `EquationSpec` 只带**一个** `scope_ref`，而
`ModelSpec` 只能引用自己 `problem_refs` 之内的对象（`ir/refs.ts` 的
`validateScopeOwnership`，REF-003）。于是"**全局假设**"在 IR 里**无法表达**——
模型正确识别出"各零部件的次品事件相互独立"适用于全部 4 问，声明一条 `A-INDEP`
并在 4 个 ModelSpec 里引用，被拒。

**修法**：给两个契约对象加一个可选字段 `shared: boolean`。

- 作用域仍指向它**推导自**的子问题（保持溯源）；
- `shared: true` 时，**任何**子问题的模型都可以引用它；
- 归属检查据此放行。

**不变量没有被削弱**（这是本次修复的验收点）：一条**没有**声明 `shared` 的假设被
跨子问题引用时，**照旧拒绝**。规则原本要防的"借另一个子问题的假设来给自己背书"
仍然被防住；放宽的只是"声明者明确说了它对所有子问题成立"这一种情形，而那种情形
本身是可审计的（字段在 IR 里，进指纹）。

**测试**（`tests/ir/ir-semantics.spec.ts`）：
- 正例：`shared: true` 的跨作用域引用**被接受**（store 层与 `validateScopeOwnership` 层各一条）；
- **负对照**：同一条链上，没声明 `shared` 的跨作用域引用**仍被拒**；
- schema：`shared` 可选、必须是 boolean（`.strict()` 不再拒它）。

**教学**（这是让模型真的用上它的那一半）：最小宪法与 `skills/paper-contract.md` 都
改成了教 `"shared": true`，并**明确否掉**了那个记账式绕法——"不要把同一条假设抄成
四份不同 id 的副本：那是记账，不是建模"。

## 3. 修复后剩下的失败（全部是可操作的正常门禁）

| 拒绝原因（原文摘要） | 性质 |
|---|---|
| `code run refused: physical key 'S_P1' does not resolve to any declared SymbolSpec (declared tokens/ids: p0 / S-P0, n / S-N, c / S-C, X / S-X)` | 命名不一致：写了 `S_P1`（下划线），声明的是 `S-P0`（连字符）。**拒绝信息直接列出合法取值** |
| `report render refused: a conclusion claim must name ≥1 quantity_ref` | 结论 claim 没有绑定任何量 |
| `the paper's prose chapters do not meet the element contract: 模型评价与推广——缺要素：优点、局限、推广；代码附录——没有说明实现了哪几问：缺 R-Q1…R-Q4` | 章节要素不全（**逐条点名缺什么**） |
| `provider returned HTTP # with an empty stream` ×3 | 传输层：中转返回空流，已被重试机制吃掉 |

**这四条与第一轮的性质完全不同**：第一轮是"契约表达不了模型的建模意图"（模型没错，
契约缺能力）；这一轮是"模型自己的声明有瑕疵"（命名不一致、要素不全），而且
**每条拒绝都给出了修法**。后者才是门禁该有的样子。

## 6. 下一轮该做什么

现在瓶颈已经从"契约缺能力"变成了"模型声明有瑕疵"，而后者是**模型可以被教好的**。
最直接的下一步是**针对本轮的四条下游拒绝各加一条产出前教学**：

| 本轮拒绝 | 该加的教学 |
|---|---|
| `S_P1` 不解析 | 已在宪法里（"use the exact token or symbol_id"）——但模型没照做。应把**常见错法**（下划线 vs 连字符）写进 `skills/evidence-and-numbers.md` |
| 结论缺 quantity_ref | 已在宪法里。同上，需要把"claim 必须绑量"提到更靠前的位置 |
| 评价章缺要素 / 代码附录没点名 | 已在 `skills/writing-norms.md` 与 `paper-contract.md`。**模型没去读**——这是 L1 的第一个待测项（"模型会不会真的去读技能库"）|

**这四条指向同一个待测问题**：规则都写在技能库里了，**模型读不读？** 如果它不读，
那么"按需加载"的设计前提就不成立，需要改成"关键规则仍然前置"。

→ **下一轮（strict × 1）的观测重点**：从 prompt 里查模型有没有 `read_file` 技能库；
以及那四条教学是否被触发。
