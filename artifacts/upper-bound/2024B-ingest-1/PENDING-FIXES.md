## P0 阶段 8 复核报出的 4 条致命建模缺陷 ⛔ **优先级最高（高于图片问题）**

- **状态**：待修（**复核判定 `gate_decision: ROLLBACK`、`gate_status: BLOCKED`，

- **证据**：`stages/08-review/COMP_REVIEW_VERDICT.json`（`fatal_count: 4`，
  `counts_by_severity: {fatal:4, major:6, minor:0}`）；完整报告 `COMP_REVIEW.md`
- **四条致命**（复核原文摘要）：
  1. **F-001 `task_misread`（owner 02-modeling）**：题面只固定 p0=10% 与 95%/90% 信度，
     而规划式还依赖 Δ、β——**送审材料没给数值也没给业务依据**，当前只有键名与占位。
     提高 β 会放松功效并改变最小 n，改变 Δ 会改变 p_alt。
     **影响：问题 1 的核心交付不可识别、不可复算。**
  2. **F-002 `cross_problem`（owner 02-modeling/03-code）**：`U_v` 被定义为"每件**合格交付物**
     的等效成本"，但 Z_v=0 时直接令 `U_v = K_f(v)`——**漏了除以交付概率 q_v**。
     以 A_v=8、q_v=0.9 为例，正确值是 `(8+B)/0.9`，模型给的是 `8+B`；
     父节点随后同时用该 U_v 与 Q_v，**形成混合单位**。
     **影响：所有不检测中间节点的成本、利润、DP 状态与最终决策均可能错误。**
  3. **F-003 `cross_problem`（owner 02-modeling/03-code）**：根节点 Z_f=0 分支把调换损失
     与拆解费**整项删掉**。实例给成品条件次品率 10%、调换损失 40 元，即使子件全合格也有
     q_f=0.9；按每件合格品口径仅调换项就应是 `0.1×40/0.9 = 4.444…` 元。
     **影响：根利润、D_f 决策、问题 3 整树结果与问题 4 重解全部失真，且不可能退化到问题 2。**
  4. **F-004 `task_misread`（owner 02-modeling/03-code）**：`p_hat=x/n` 与 Clopper–Pearson
     区间依赖实际 x，但材料没有每个部件的 (n_v, x_v)，只说"从同一批登记参数生成新样本"。
     若生成中心是已知真值参数，那只是**真值条件模拟**，不是已观测抽样估计。
     **影响：问题 4 的核心交付——抽样误差下重做 Q2/Q3——没有实际被重做。**
- **复核自己的诚实边界**（原文）：*"本复核与建模、编程共享题面解释，且本次未提供实际代码和运行账本，

- **证据**（逐张目视，可复现）：
  - `stages/06-figure/figures/fig_q2_recovery_cost_compare.png`：中位数标注
    「U 中位数 36.63」「中位数 22.62」右半被裁，只剩前几个字。

    被挤成窄条，横轴标题也被裁。
  - `stages/06-figure/figures/fig_q3_assembly_network_cost.png`：底部横轴标题被裁。
- **为什么先放行**：图数与结构已达标（**14 张 ∈ 12–18**、9 种图型、14/14 用 `_figbase`、
  多面板 4 张），这些排版缺陷**不改变数据与结论**；卡在排版上会挡住整条流程的其余阶段。
- **⚠ 根因已查清（2026-09-28 更正，此前判断有误）**：**钳制本身是自动的**——
  `plot_utils` 的 `savefig` 钩子链里已自动调 `_auto_fix_overlaps` → `_clamp_texts_to_axes`，
  另有 `_pull_back_outside_transaxes_text`。所以**不是"脚本没手写钳制"**（我先前与子代理
  都这么以为，是错的；一度想把"未使用辅助函数"升为硬拦，已否决）。
  真实机制写在源码注释里：`_save` **刻意**用 `bbox_inches=None`（防 PDF mediabox 被
  axes 外标注撑爆），代价就是**画布边缘会切掉画到外面的文字**；两个兜底只覆盖
  **刻度标签**与 **transAxes 的上下越界**，**右侧 / 数据坐标越界不在其中**——这正是三张图
  被裁的位置。
- **拟修法（改为渲染层，不再动契约）**：
  1. 在 `_figbase.save()`（**我们自己的文件**，不是原样迁移的 `plot_utils.py`）里，保存前
     遍历 figure 的文字对象，把窗口范围超出画布的**拉回画布内**（右侧优先）；
  2. 或对 **PNG** 输出改用 `bbox_inches='tight'`——`bbox_inches=None` 的理由是 **PDF**
     mediabox，而本链路是 PNG（docx 用），tight 反而正好把越界文字纳进画布。
  3. `figure_text_within_axes` 这条**脚本层**判据保留（它抓字面量坐标的明显越界），
     但**不承担**修 P1 的责任——三条真实被裁的坐标都是表达式/`transform`，静态判不出来。
- **验收判据**：三张点名图的标注**完整可见**（右边界不再切字）；14 张逐张目视无裁切；
  `figure_text_within_axes` 在阶段 6 报 `0`。

## P3 生成脚本的 API 兼容 bug 靠手修（应改为环境约束前置）

- **状态**：**已修（2026-09-28）**。四类 API 误用已进 `figure_script_quality` 硬判据（含 `scatter` 标量广播的明显形态）；契约已写明正确写法；**并修掉了配方库自身教错写法的那一处**（`figure_recipes_advanced.md` 与 `skill-docs` 镜像里的 `nx.draw_networkx_nodes(..., zorder=3)`——契约要求照抄配方，而门禁会拦它，这是"教了又拦"）。验证：真实 14 个脚本上 `figure_script_quality` 报 `0`（零误杀）。
- **现象**：脚本在**渲染阶段**崩溃，四类 API 误用：
  1. `mcolors.ScalarMappable` —— matplotlib 3.10 起不在 `matplotlib.colors`（改用 `plt.cm`）；
  2. `nx.draw_networkx_edges/nodes/labels(zorder=…)` —— 该版 networkx 不接受 `zorder`；
  3. `set_xlim(bottom=…)` —— `bottom` 是 y 轴的关键字，x 轴是 `left`；
  4. `scatter(标量, 数组)` —— matplotlib 不做标量广播（`x and y must be the same size`）。
- **为什么要紧**：这类崩**只在最后一步（渲染）暴露**，等于把代价推到整轮末尾；
  而且**每新生成一代脚本就会重犯**（本轮就重犯过一次）。
- **拟修法**：
  1. 把上述四条**环境 API 约束写进阶段 5 简报**（与 `_figbase` 的色板形状同类：契约要教对形态）；
  2. `figure_script_quality` 加静态检查：出现 `mcolors.ScalarMappable` /
     `draw_networkx_*(` 同块内 `zorder=` / `set_xlim(bottom=` 即报（这几条都是**确定性**的文本判据，
     零误报风险）。
- **验收判据**：新生成的一代脚本**零手修**即可全绿渲染；门禁对上述四条各有一条回归测试。
