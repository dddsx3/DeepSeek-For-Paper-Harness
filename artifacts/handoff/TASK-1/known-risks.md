# Known risks (deferred)

Risks discovered while implementing TASK 1, explicitly out of scope and
deferred per task book §20 and §21. The presence of an entry here is **not** a
failure; the presence of a **fixed-but-undocumented** risk in this commit
**is** a failure.

| ID | Description | Why deferred | Target TASK |
|----|-------------|--------------|-------------|
| RISK-01 | **External locators are not resolved.** `raw_problem_ref`, `code_ref`, `input_refs`, `output_refs`, `stdout_ref`, `stderr_ref` and `Result.source_location` are only checked for non-emptiness. A `RunArtifact` may therefore name an output file that does not exist. The IR has no filesystem by design, so proving the bytes exist belongs to the execution gate. | Adding a filesystem probe to the IR would couple canonical state to I/O and make ingest non-deterministic. | TASK 3 (Gate B) |
| RISK-02 | **`ProblemSpec.raw_problem_ref` has no hash.** The raw problem statement is the root of the provenance graph but is an opaque URI, so "the problem text changed under us" is undetectable. | DataArtifact does not exist yet; hashing the raw problem is the same mechanism. | TASK 1.5 |
| RISK-03 | **Nested ids are unique inside their parent only.** `subproblem_id` / `output_id` may collide across two `ProblemSpec` objects, and are not addressable as reference targets. | Global nested-id ids belong to the Requirement Registry's id space. | TASK 1.5 |
| RISK-04 | **`seed: null` is admitted.** A run with no recorded seed can enter canonical state. | The IR records facts; gates enforce policy. Rejecting `null` would block legitimate non-deterministic exploratory runs. | TASK 3 (Gate F) |
| RISK-05 | **`FigureSpec` is schema-only** (`figure_id`, `data_refs`, `claim_refs`), and `data_refs` resolves to `Result` because `DataArtifact` does not exist yet. | Task book §7 says "第一阶段只定义 schema". TASK 1.5 widens the target; TASK 7 adds the renderer fields. | TASK 1.5 + TASK 7 |
| RISK-06 | **`Result.value` is `number` only.** Categorical results (a chosen alternative, a label) cannot yet be expressed; `uncertainty` has no distribution shape. | Widening would re-open "free text is the source of truth for a core number". | TASK 2 / TASK 3 |
| RISK-07 | **No staleness machinery.** The store is append-only, so a reference that resolved at ingest can never dangle — which also means the IR cannot express "the upstream changed". | TASK 3.5 owns the dependency + STALE engine. | TASK 3.5 |
| RISK-08 | **`ModelSpec.equations` are free strings.** No `EquationSpec`, no id, no hash, so "the equation in the paper matches the equation in the model" is not machine-checkable. | Task book §16 places EquationSpec in TASK 7.5. | TASK 7.5 |
| RISK-09 | **Reviewer verdict fields are rejected, not ignored.** TASK 5 says `paper_passed` / `paper_failed` / `final_score` "即使出现也必须被忽略". This TASK **rejects** the whole finding instead, which is strictly stronger but is a different behaviour. | The stricter behaviour is fail-closed and cannot be worse for safety; TASK 5 may narrow it to field-level stripping. | TASK 5 |
| RISK-10 | **`ModelingIr` is in-memory and per-process.** Nothing persists canonical state across restarts; two stores do not share an id space. | Persistence is a composition concern; TASK -1's preflight already requires `persistence`/`artifact_store` before a FORMAL run. | TASK -1 composition / TASK 3.5 |
| RISK-11 | **`executor.ts` `parseDefects` still absorbs malformed reviewer output** into `[{ severity: 'major', description: 'reviewer returned …' }]` — exactly the "repair the rejected output" pattern this TASK forbids. It was **not** touched: changing it changes `WorkflowExecutor`'s review-loop behaviour (TASK 5's surface) and breaks existing executor tests. The IR-level `ReviewerFinding` path is the one that fails closed. | Drive-by fix would exceed the TASK's minimal-change scope (§21). | TASK 5 |
| RISK-12 | **`scanIrValue` and the schema walk are O(n) each; array fields are unbounded** beyond the 1 MiB text cap. A 200 000-element `claim_refs` array is accepted via the typed `put()` path. | The 1 MiB ingress cap bounds the realistic attack surface; per-field array caps add schema churn with little gain until a real consumer exists. | TASK 3 (gates) if consumers report it |
| RISK-13 | **`Result.value` round-trip fidelity is JSON's.** `1e-400` parses to `0`, `9007199254740993` to `9007199254740992`; the canonical value differs from the model's literal with no trace. | Rejecting non-round-trippable literals requires a pre-parse literal audit; TASK 3's numeric-consistency gate compares paper numbers against IR values, which is the cheaper place to own this. | TASK 3 |
| RISK-14 | **The IR is currently un-wired.** Nothing outside `src/ir/` and `tests/ir/` consumes `ModelingIr`; the only integration is the barrel re-export. "No illegal object can enter canonical state" is true but vacuous until a producer exists. | Per task book §1.1 core TASKs are strictly serial; TASK 2 (Claim→Result→Run evidence chain) is the first consumer and will wire the IR into the workflow. | TASK 2 |
| RISK-15 | **The barrel exports `IR_SCHEMAS` / `validateRefFields` beside `ModelingIr`.** A caller can parse with the schemas and build its own state container, re-introducing duplicate-id and dangling-ref failures. Not an escape today (schemas are strict and tables are frozen), but `put()`'s uniqueness is a convention, not a boundary. | The schemas are also the vocabulary for TASK 2/3 consumers; hiding them would break the future gates' ability to validate. | TASK 2 wiring review |
